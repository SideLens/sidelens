# NV12 几何变换：旋转、裁切、镜像、翻转

> `crates/sidelens-frame-transform`。24 项测试，跨平台可跑。

## 为什么单独一个 crate

「把一帧 NV12 转成用户想要的方向」是三处都要做的事：手机链路（横拿/竖拿）、
屏幕采集（裁掉工具栏）、预览窗口（镜像）。三处各写一份，一定会出现
「虚拟摄像头里是对的、预览里是错的」—— 两个消费者看的是同一块共享内存，
这类 bug 最难查。

抽出来还有个收益：它是纯数组运算，没有平台依赖，因此**能在 Linux CI 上**
把每一种旋转/裁切的边界都跑一遍。而在 `phone_bridge` 里它被 `cfg(windows)`
门控，只能在 Windows 上测。

## NV12 的三条硬约束

NV12 是 YUV 4:2:0 的半平面格式：Y 平面 `width × height` 字节，UV 平面
`(width/2) × (height/2)` 对（每对 2 字节，覆盖 2×2 像素）。

| 约束 | 违反的后果 | 本 crate 的处理 |
| --- | --- | --- |
| 宽高必须偶数 | 没有合法的 UV 平面 | `Geometry::new` 返回 `None` |
| 裁切偏移必须偶数 | 色度采样对不齐，一半像素 U/V 取错位置 | `Crop::new` 返回 `None` |
| 90°/270° 交换宽高 | 旋转后 UV 行宽变了，沿用旧 stride 会写错位 | `Geometry::rotated` 单独算 |

只靠注释约定这三条，调用方一定会踩。所以用类型把它们钉住，而不是写文档提醒。

## 管线顺序

```text
  输入帧 ──▶ 裁切 ──▶ 旋转 ──▶ 镜像 ──▶ 翻转 ──▶ 输出帧
            (原坐标)  (裁切尺寸)  (旋转后)
```

顺序是固定的，理由是每一步的坐标系依赖前一步的结果：

- 裁切在原坐标系里做，否则用户没法说「裁掉左上角 100×100」；
- 旋转在裁切后的尺寸上做（旋转 90° 后宽高变了）；
- 镜像/翻转在旋转后的坐标系里做（用户看到的「左右」是旋转之后的左右）。

## 实测抓到的一个 bug

第一版里 `fill_cropped_y` 用的 stride 是 `output.geometry.width()`。
在 90°/270° 旋转时这个值是**旋转后的宽度**，而拷贝还在按原方向逐行写 ——
结果行写错位，小图上直接 `range end index out of range` panic。

测试 `裁切后旋转的尺寸是裁切尺寸的旋转` 和 `九十度旋转把左上角搬到右上角` 抓到它。
修法是把 stride 显式算成 `cropped.width()`，并在代码里写清为什么不能用 output 的宽度。

另一处：`输出缓冲区尺寸不符时拒绝` 这条测试最初用了 8×8 的正方形 ——
正方形旋转 90° 后几何不变，测不出尺寸校验。改成 8×4 才有效。
**测试夹具选得不对，会让一条本该有用的断言变成永远通过**，这一条值得记下来。

## 在手机链路里怎么用

控制消息新增两个字段：

```json
{ "rotate": 90 }
{ "crop": "100,50,1280,720" }
{ "rotate": 0, "crop": "" }
```

非法值不会静默忽略：「忽略非法旋转角度 45（只接受 0/90/180/270）」会打到日志。

### 与 DirectShow 协商模式的冲突

DirectShow 客户端选定 1920×1080 后，接收端会被要求按那个尺寸解码输出。
如果用户同时要求旋转 90°，结果是 1080×1920 —— **与协商模式不符**。

处理方式是：检测到尺寸不符就跳过变换并打一次日志（同一会话只打一次，
否则 60fps 会把日志刷爆），明确告诉用户「请让客户端选择旋转后的分辨率」。
悄悄塞一个尺寸不符的帧会让下游按错误 stride 解读共享内存 —— 那是最坏的结果。

## 性能

纯 CPU 逐像素，没有 SIMD。1080p 一次旋转约 200 万次索引运算。
这条路径只在用户显式开启旋转/裁切时才走（`Transform::is_identity()` 为真时
整帧跳过），因此默认配置下零开销。

要优化的话，正确顺序是：先加 `apply_into` 的缓冲区复用（已经提供），
再考虑按行整块 `copy_nonoverlapping` 替代逐像素索引 —— 90°/270° 的换行
拷贝才是真正的开销，SIMD 解决的不是主要矛盾。

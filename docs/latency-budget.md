# 延迟预算（第二十八、二十九轮更新）

> 这一篇算清「20.95ms 里每一毫秒花在哪」，以及哪些是可优化的。

## 一、历史记录是怎么来的

`latency-matrix.md` 里长期记录的是 **`playable_ms` p50 = 20.95ms**。
那个数字在第二十八轮之前是**结构性的常量**，不是实测优化结果：

```text
playable_ms = now - send_ts_us
            = 网络传输 + 接收处理 + 抖动缓冲等待
```

而抖动缓冲的 `target_ms` 恒为 `JitterConfig::default()` 的 **20.0**
—— 因为 `shrink()` / `grow()` **从未被调用**（见 `progress.md` 第二十八轮）。

所以：

```text
20.95 = 20.00（纯等待，常量）+ 0.95（真实传输 + 处理）
```

**延迟优化的全部空间都在那个 20.00 上。**

## 二、当前分解（回环，60fps，8KB 帧）

| 组成 | 值 | 可优化？ | 依据 |
| --- | --- | --- | --- |
| 抖动缓冲等待 | **10.0 ms** | ✅ 已从 20 降到下限 | `adapt` 按实测抖动调整，`min_ms=10` |
| 编码（H.264） | 1.55 ms | ⚠️ 硬件编码器 | `encode_avg_us=1544` |
| 协议编解码 | < 0.001 ms | ❌ 已到底 | 59ns 编码 / 104ns 解码（8KB） |
| UDP + 内核 | ~0.2 ms | ❌ | `net_ms` p50 |
| 重组 + FEC + 解密 | ~0.2 ms | ❌ | `perf-audit` 实测 1.21µs/包 |
| 1ms tick 粒度 | 0-1 ms | ⚠️ 已用 `timeBeginPeriod(1)` | 见 `progress.md` 第 4 项 |
| **合计 p50** | **13.77 ms** | | 实测 |

`min_ms = 10` 是**刻意的下限**，不是没优化完：

- UDP 乱序在 WiFi 上 10-30 个包很常见
- 内核调度抖动在 1ms tick 下就有 0-1ms
- 再小会把正常乱序判成迟到帧，**丢帧的代价远大于 2ms 延迟**

## 三、跨网络时的预期

`target_ms` 会按实测抖动自适应，所以不同链路的表现不同：

| 链路 | 典型抖动 | `target_ms` 收敛值 | 预期 p50 |
| --- | --- | --- | --- |
| 本机回环 | 0.04-4 ms | 10（下限） | 13.8 ms |
| 局域网 WiFi 5GHz | 2-8 ms | 10-20 | 15-25 ms |
| 局域网 WiFi 2.4GHz | 10-30 ms | 25-75 | 30-80 ms |
| 公网同城 | 5-15 ms | 12-38 | 20-45 ms |
| 公网跨城 | 15-40 ms | 38-100 | 45-110 ms |
| 公网跨境 | 40-120 ms | 100-200（上限） | 110-210 ms |

公式：`target_ms = clamp(jitter_ewma × 2.5, 10, 200)`

系数 2.5 的依据：`jitter_ewma` 是 `0.9/0.1` 平滑后的**均值**，乘 2.5 大致覆盖 3 sigma。
小于 2 会在抖动轻微变大时开始丢帧，大于 3 则退化成「不敢降」。

**这些是推算，不是实测** —— 本机只有回环可用（见 `blockers.md` B1/B2）。
拿到第二台设备后应重跑 `tools/bench/run-matrix.ps1`。

## 四、升 vs 降的不对称（重要）

`adapt` 的两个方向行为不同：

| 方向 | 行为 | 理由 |
| --- | --- | --- |
| 升（抖动变大） | **全额立即生效** | 抖动变大时每一帧都在丢，等不起 |
| 降（抖动变小） | 单次最多 2ms + 200ms 驻留期 | 降错了的代价是**丢帧**（可见卡顿），升错了只是多一点延迟（不可见） |

从 20 降到 10 需要 **5 次调整 = 10 秒**（2 秒报告间隔 × 5）。
这在会话开始时是一次性的，之后只在链路变化时微调。

## 五、三个已经排除的优化方向

| 方向 | 为什么不做 |
| --- | --- |
| 把 `min_ms` 降到 5 或 2 | 会把正常 UDP 乱序判成迟到。丢一帧的可见代价 >> 2ms 延迟 |
| 取消抖动缓冲（target=0） | 帧到达即播，网络任何抖动都直接变成画面抖动 |
| 用更小的 tick（如 0.5ms） | Windows 的 `timeBeginPeriod` 最小就是 1ms；再往下要改内核定时器，代价远超收益 |

## 六、还没做的

| 项 | 预期收益 | 阻塞 |
| --- | --- | --- |
| 硬件 H.264 编码器（NVENC/QSV） | 编码 1.55ms -> ~0.3ms | 需要实现异步 MFT 路径 |
| 接收端零拷贝渲染 | 未知 | 需要真实消费端（相机应用） |
| 音频侧 `target_ms` 也做自适应 | 音频当前固定 40ms | 音频不重传，抖动容忍度不同，要单独设计 |

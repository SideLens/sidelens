# H.264 码流处理（nalu.rs）的三个实测 bug

> 来源：`sps-parse` 子代理在实现 SPS 解析时写探针程序实测发现的
> 修复与回归测试：主线
> 状态：**已修复，9 项回归测试钉住**

## 为什么这些 bug 值得单独一篇

三个都不会崩溃、不会报错、不会打异常日志 —— 它们只是让**错误的数据流过去**。
这类 bug 的特征是：

- 单元测试全绿（因为测试本身是按错误假设写的）
- 功能「看起来能用」（大多数码流恰好不触发）
- 出问题时症状在很远的地方（花屏、黑屏、解码器报错）

---

## Bug 1（最严重）：无起始码的碎片被当成 NALU → 垃圾被缓存成 SPS

### 原实现

```rust
if codes.is_empty() {
    // 没有起始码：整段当一个 NALU（某些编码器会省略首帧起始码）
    out.push(NaluView { ty: NaluType::from_header(buf[0]), data: buf });
    return out;
}
```

### 攻击链（实测）

```text
输入 [67 1f 2a 88 99]（一段 UDP 分片中途的字节，0x67 只是碰巧出现）
  → ty = NaluType::from_header(0x67) = 0x67 & 0x1f = 7 = Sps
  → ParameterSets::update_from 把它缓存成 SPS
  → to_annexb() 把它前置到关键帧前发给对端
  → 对端解码器拿到垃圾参数集
  → 整路视频黑屏
```

**一个字节的巧合就能让整路视频黑屏。**

### 为什么原来的理由站不住

注释说「某些编码器会省略首帧起始码」。但代码**无法区分**这两种情况：

| 情况 | 应该怎么处理 |
| --- | --- |
| 真的是一帧没有起始码的裸 NALU | 当 NALU |
| 一段不含起始码的碎片（UDP 分片、丢包残片、AVCC 误喂） | **丢掉** |

而后果**不对称**：误判成 NALU 的代价是整路黑屏；误判成空白的代价是
「真的省略起始码的码流解析不出来」—— 而那个场景在真实码流里几乎不存在
（Annex-B 的定义就是带起始码）。

### 修法

```rust
if codes.is_empty() {
    // 没有起始码就不是 Annex-B，返回空
    return out;
}
```

需要「宽容模式」的调用方应该自己包一层（或先用 AVCC 解码）。

## Bug 2：尾随 0 裁剪吃掉 `cabac_zero_word`

### 原实现

```rust
while trimmed_end > data_start && buf[trimmed_end - 1] == 0 {
    trimmed_end -= 1;
}
```

### 实测

```text
输入 [0001][65 88 84 00 00][0001][41 22]
  IDR 长度 = 3（应为 5），data = [65 88 84]
```

H.264 规范 7.4.1 允许 **CABAC 码流在 NALU 末尾追加 `cabac_zero_word`
（就是 `00 00`）**。那是**切片数据的一部分**，不是填充。

裁掉后 NALU 长度错 2 字节 —— 对硬件解码器是「NALU 长度与内部 slice
长度不一致」，轻则报错重则花屏。

### 为什么原来的理由也站不住

注释说「数据末尾的 0 可以靠 RBSP 长度判断」。但 H.264 的 RBSP 长度
**没有**显式字段，只能靠 `rbsp_stop_one_bit` 反向定位 ——
而 `cabac_zero_word` 恰好破坏了那个定位。

### 修法

只裁「明确是填充」的那部分：**保留最多 2 个尾随 0**（cabac_zero_word），
超过的才算填充。最后一个 NALU（没有下一个起始码做参照物）**完全不裁**。

```text
... 65 88 84 00 00 | 00 00 01 41 22
                 ^^^^^^ cabac_zero_word，保留
                       ^^^^^ 前两个归起始码，多出的算填充
```

## 设计缺陷 3：前置填充 0 产生幽灵 NALU

### 现象

```text
输入 [00 00 00 00 01 67 42 00 1f]
  i=0: buf[3]=0 ≠ 1 → 不匹配
  i=1: 匹配 00 00 00 01 → codes[0] = (1, 4)
  → buf[..1] = [00] 被当成 NALU，ty = Other(0)   ← 幽灵
```

### 影响

幽灵 NALU 本身不致命（`is_keyframe` / `ParameterSets` 都按类型过滤），
但 `annexb_to_avcc` 会把它写进 AVCC，污染下游。

### 修法

前缀里只要有**任何一个非零字节**才算真数据：

```rust
if head.iter().any(|&b| b != 0) {
    out.push(...);
}
```

## 另外两个「不在 nalu 层」的问题（已记录，未修）

### 4. 不校验 `forbidden_zero_bit`

`NaluType::from_header(0xE7)` → `Sps`。bit 7 为 1 是规范明令的
「码流损坏」标志，`nalu.rs` 完全忽略。

这个校验放在 nalu 层比放在 sps 层更合适（PPS / 切片同样需要）。
`sps.rs` 已在自己的解析里补了 `reserved_zero_2bits != 0` 的检查，
但 `forbidden_zero_bit` 需要 nalu 层改。

### 5. `ParameterSets` 只存「最后一份」

- 多 `seq_parameter_set_id`（SVC/MVC、双路合流）会互相覆盖
- `update_from` 每帧都 `to_vec()` 比较+克隆，1080p 码流里每帧一次是白白的堆分配
- `is_keyframe` 只认 IDR(5)，不认 SEI recovery point（`nal_unit_type=6`
  里的 `recovery_frame_cnt`）—— 对「开放 GOP + 周期性 intra refresh」
  的编码器会漏判关键帧

## 回归测试（9 项）

`crates/sidelens-codec/tests/nalu_regression.rs`

| 测试 | 守什么 |
| --- | --- |
| `无起始码的输入必须返回空` | Bug 1 的直接断言 |
| `碎片不得污染参数集缓存` | Bug 1 的完整攻击链（含 `to_annexb` 输出检查） |
| `真起始码仍然正常切分` | 修复不能弄坏正常路径 |
| `前置填充零不得产生幽灵_nalu` | 缺陷 3 |
| `前置非零数据仍然算一个_nalu` | 缺陷 3 的反向保护 |
| `cabac_zero_word_不得被裁掉` | Bug 2 |
| `额外的填充零仍然被裁` | Bug 2 的反向保护 |
| `最后一个_nalu_不裁尾随零` | Bug 2 的边界 |
| `修复后_avcc_转换不含空_nalu` | 下游污染 |

另外**改写了 3 个原有测试的断言**（它们本身是按错误假设写的）：

| 文件 | 原断言 | 新断言 |
| --- | --- | --- |
| `tests/nalu.rs` | 无起始码 → 1 个 NALU | 无起始码 → 0 个 NALU |
| `tests/nalu.rs` | 尾随 0 全裁（4 个 0 → 长度 5） | 保留 2 个（长度 7） |
| `tests/annexb_edge.rs` | 1 个尾随 0 被裁 | 保留（可能是 cabac_zero_word） |

**改测试断言是这轮最该记住的一件事**：当一个 bug 被发现时，
「测试全绿」说明测试本身也错了。只改代码不改测试，下次会有人
「修复」回去。

## 为什么这个 bug 能活这么久

它经过了：
- 26 个 `nalu.rs` 单元测试
- 6 个 `annexb_edge.rs` 边界测试
- 多轮端到端实测（UDP + FEC + 加密 + 音频）

全部通过。原因是**所有测试都按同一套错误假设写的** ——
「无起始码就是一个 NALU」「尾随 0 都是填充」。

发现它的人是 `sps-parse` 子代理：它在写 SPS 解析器时**必须**理解
NALU 结构，于是写了个探针程序逐字节验证，才看出这两处。

**教训**：单测覆盖率不能证明正确性，只能证明「实现符合写测试时的理解」。
真正能证伪的是「用一个独立的、更底层的视角重新实现一遍」。

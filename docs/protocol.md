# SideLens 帧协议 v0

## 1. 为什么要有自定义帧格式

WebSocket 的 message 边界不是"帧"的边界：一条视频帧可能被拆成多条 message，也可能多条挤在一条里。
接收端必须能**从任意切分的字节流里**重新切出帧，否则一旦发生网络重传或 TCP 合并，整条流就废了。

所以协议必须自带：**magic + 长度**。

## 2. 帧头（32 字节，小端）

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 4 | magic | `53 4C 4E 30`（"SLN0"） |
| 4 | 1 | type | 0=HELLO 1=CONFIG 2=VIDEO 3=AUDIO 4=KEYFRAME_REQ 5=STATS 6=BYE |
| 5 | 1 | flags | bit0 = keyframe |
| 6 | 2 | streamId | 0=视频主路，1=音频 |
| 8 | 4 | seq | 每路独立递增 |
| 12 | 8 | ptsUs | 单调时钟，微秒（uint64） |
| 20 | 8 | sendTsUs | 发送时刻，微秒（uint64） |
| 28 | 4 | payloadLen | 载荷长度 |
| 32 | N | payload | 视频/音频裸数据，或控制帧的 UTF-8 JSON |

32 字节头对 1080p 的 8KB 典型帧来说是 0.4% 开销，可以接受。
若将来要传极小帧（如音频 20ms 一包约 200 字节），可考虑压缩头到 16 字节。

## 3. 时钟同步（关键）

**坑已经踩过**：`performance.now()` 的零点是**进程启动时刻**，两个进程相减得到的不是延迟，
而是「两个进程启动时间差 + 真实延迟」。demo 第一次跑出 7148ms 就是这个原因。

正确做法（已实现于 `packages/proto/src/index.js` 的 `nowUs()`）：

```js
BigInt(Math.round((performance.timeOrigin + performance.now()) * 1000))
```

`timeOrigin` 把零点对齐到 Unix 纪元，同一台机器上的多进程共享时基。

**跨设备时钟协商：已实现并验证（第五十六轮）。**

协议用 `RTT_PROBE` / `RTT_REPLY` 两个帧类型做 NTP 式四时间戳协商：

```text
本端                     对端
  |  RTT_PROBE (nonce, t1)  |      t1 = 本端发出时刻
  | ----------------------> |
  |                         |      t2 = 对端收到时刻
  |  RTT_REPLY (t1,t2,t3)   |      t3 = 对端发出时刻
  | <---------------------- |
  |  t4 = 本端收到时刻       |
```

### 四个时间戳的时基归属（最容易搞混的地方）

| 字段 | 谁打的 | 时基 |
| --- | --- | --- |
| `t1` | 本端发出探测时 | **本端** |
| `t2` | 对端收到探测时 | **对端** |
| `t3` | 对端发出回复时 | **对端** |
| `t4` | 本端收到回复时 | **本端** |

于是：

- `t3 - t2`：同源 → 对端处理时间
- `t4 - t1`：同源 → 本端看到的往返总时长
- `t2 - t1` / `t3 - t4`：**跨时基**，各带一个时钟差

### 两个公式

```text
offset = ((t2 - t1) + (t3 - t4)) / 2      // 跨时基的两项平分出差值
rtt    = (t4 - t1) - (t3 - t2)            // 两个同源差值相减
```

`offset` 的语义是「**本端时刻 = 对端时刻 + offset**」，与 `ClockSync::to_local()`
的 `peer + offset` 一致。

### 样本选择：取 RTT 最小的那个

窗口保留最近 N 个样本，用**RTT 最小**的那个作为当前估计。
理由：RTT 越小，去程/回程越对称，offset 的偏差（`(去程-回程)/2`）越小。

### 实测：±500ms 时基偏移下音画仍对齐

用 `--clock-bias-us` 注入人为偏移（只偏移载荷 PTS，不偏移 t1/t4）：

| 注入偏移 | 发送端 `offset_ms` | 接收端 `playable_ms` | `dropped` |
| --- | --- | --- | --- |
| 0 | 0.05 | 18.79 / 27.64 | 0 |
| **+500ms** | **-2.54** | 19.00 / 27.35 | **0** |
| **-500ms** | **-0.53** | 18.90 / 27.86 | **0** |

说明 `to_local()` 的换算链路是通的：发送端 PTS（对端时基）→ `to_local()`
换算到本端时基 → AvSync 裁决 → 出队播放。

### 一个踩过的坑

`t1` 与 `t4` **必须同源**（都是本端时基）。一度把 `t1` 也加了偏移，
导致 `t4 - t1` 为负、探测被静默丢弃、`synced` 永远 false。

要模拟跨设备时基差异，只能偏移**载荷里的 PTS**，不能偏移本端自己的计时。

## 4. 为什么 demo 用 WebSocket 而不是 QUIC

QUIC 需要：QUIC 库 + UDP 打洞 + 自签证书 + 多路复用调度。
这些会淹没「能不能跑通」这个核心问题。

但**接口按 QUIC 的语义设计**：`send(frame)` 是"尽力发出"，不承诺有序可靠。
将来把 `transport.js` 换成 quinn（Rust）或 node:quic 时，上层（jitter / clock / session）不用改。

## 5. 版本演进

| 版本 | 帧类型 | 内容 |
| --- | --- | --- |
| v0 | 0-6 | HELLO / CONFIG / VIDEO / AUDIO / KEYFRAME_REQ / STATS / BYE |
| v1 | 7-11 | NACK / RETRANSMIT / FEC / RTT_PROBE / RTT_REPLY |

flags 位定义：

| 位 | 名称 | 含义 |
| --- | --- | --- |
| bit0 | FLAG_KEYFRAME | 关键帧 |
| bit1 | FLAG_RETRANSMIT | 重传帧（接收端据此区分首传与重传，避免重复统计） |
| bit2 | FLAG_FRAGMENT | 分片（UDP 传输时一帧切成多个包） |

## 6. NACK（丢包重传）

### 为什么需要

视频帧之间有依赖：丢一个 P 帧，后续所有帧都解不出来，只能等下一个关键帧
（可能 2 秒后）。NACK 让接收端说"我缺 12、13 帧"，发送端从缓存重发，
把 2 秒卡顿压到 1 个 RTT。

### 三种抗丢包方案的取舍

| 方案 | 延迟开销 | 带宽开销 | 适用 |
| --- | --- | --- | --- |
| 逐包 ACK | 1 RTT | 小 | 可靠传输 |
| **NACK（本方案）** | **1 RTT** | **小** | **实时视频** |
| FEC 前向纠错 | 0 | 大（+20~50%） | 高丢包、极低延迟 |

选 NACK：实时视频绝大多数包能到，为少数丢包付 1 个 RTT 比长期牺牲 30% 带宽划算。
FEC 保留（`FrameType::Fec` 已占位）。

### 载荷格式

```json
{"stream": 0, "seqs": [12, 13, 15]}
```

序号升序、去重，单次最多 `max_batch` 个。

### 延迟请求：为什么不能立刻请求

网络乱序会让 seq 3 比 seq 2 先到。立刻请求 seq 2 会导致：
重传的 seq 2 到达时，原来的 seq 2 可能已经到了 —— 白费一个 RTT 和一份带宽。

所以等 `nack_delay_ms`（默认 5ms）再请求，让乱序的包先到齐。
实测这个延迟能把误报率从"每次乱序都误报"降到接近 0。

代价：真的丢包时，恢复延迟多了 5ms。这个 `取舍` 在弱网（乱序多）时值得，
在好网（几乎不丢）时也无害 —— 因为压根不会触发。

### 发送端缓存策略

| 约束 | 值 | 理由 |
| --- | --- | --- |
| 最多缓存帧数 | 300 | 8KB × 300 ≈ 2.4MB，覆盖 5 秒 @60fps |
| 最多缓存字节 | 8 MB | 防止大 I 帧把内存吃爆 |
| 最长存活 | 5 秒 | 更旧的重传到达时早已过播放时刻，白费带宽 |
| 单帧最多重传 | 3 次 | 超过说明链路极差，再传也是徒劳 |

**关键帧永不淘汰。** 如果请求关键帧后那个关键帧已被淘汰，接收端就永远恢复不了。
这是个死锁，必须用"关键帧不参与淘汰"来避免。

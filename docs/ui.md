# 原生 UI 层（`sidelens-ui`）

> 纯 Win32 控件 + DPI 感知 + 非阻塞消息泵。**不用 webview**。
> `pump` 实测 **297 ns/次**，1ms tick 的 0.03%。

## 为什么不用 webview / Electron / Tauri

用户对 SideLens 的原始要求：「超低的连接延迟、**极致的原生 ui 性能体验**，
哪怕不同系统的 ui 界面用不同的框架来写都可以」。三条硬指标直接排除 webview：

| 方案 | 启动 | 常驻内存 | 滚动/动画 |
| --- | --- | --- | --- |
| webview（WebView2） | 数百毫秒（首次更久） | 几十 MB | 合成器掉帧，1ms tick 下尤其明显 |
| **纯 Win32 控件** | **数十毫秒** | **几 MB** | 系统原生，无掉帧 |

而这个软件的界面复杂度是「几行状态文字 + 一块视频 + 几个开关」——
原生控件的开发成本并不高，收益却是实打实的。

## 分层

| 层 | 模块 | 编译条件 | 内容 |
| --- | --- | --- | --- |
| 跨平台 | `dpi.rs` | 无条件 | 逻辑/物理像素换算、字体磅值换算 |
| 跨平台 | `layout.rs` | 无条件 | 锚点平移、视频区增长、矩形缩放 |
| 跨平台 | `control.rs` / `event.rs` / `error.rs` | 无条件 | 句柄、事件、错误 |
| Windows | `win32.rs` | `cfg(windows)` | 真窗口、真控件、真消息泵 |

**前四层是纯函数，在 Linux CI 上能跑全部单元测试。**

这不是洁癖：DPI 换算错一次，界面在 200% 缩放下就会小一半，
而这种错误在开发机的 100% 屏幕上永远看不出来 —— 只有把算术从 Win32 里
拆出来，才可能用一组 DPI 值把边界钉死。

## 实测性能（3840x2160 @200%）

| 操作 | 耗时 |
| --- | --- |
| 建隐藏窗 | **2.4 ms** |
| 建 10 个控件 | 4-5 ms |
| `pump` 空转 | **223-297 ns/次** |
| `show()` | 7.5-8.4 ms（DWM 首次合成） |

**`pump` 297ns 是关键数字** —— 主循环是 1ms tick，如果 `pump` 要 100µs
就吃掉 10%。297ns 占 0.03%，完全无感。

`show()` 的 7.5ms 是 DWM 首次合成；裸 Win32 对照是 60-110ms（非本 crate 成本）。

## 四个必须做对的点

### 1. DPI 感知

`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`。失败不算错误
（宿主可能已设过，返回 `ACCESS_DENIED`）。

不做的话 4K + 200% 缩放下界面会小一半。

### 2. 字体必须按 DPI 重建

`CreateFontW` 的 `lfHeight` 要按 DPI 算。`WM_DPICHANGED` 时销毁旧字体、
建新字体、重新布局。不做的话文字在 4K 屏上会小到看不清。

### 3. 不要用 Win32 默认字体

默认控件字体是 `SYSTEM_FONT`（很丑的位图字体）。必须
`SendMessageW(hwnd, WM_SETFONT, font, 1)` 给每个控件设字体。
推荐 `Microsoft YaHei UI`（中文），fallback `Segoe UI`。

### 4. 消息泵不能阻塞

`pump()` 必须用 `PeekMessageW`（非阻塞）而不是 `GetMessageW`（阻塞）——
调用方是 1ms tick 的主循环，阻塞会让视频卡住。

## 在 daemon 里怎么用

```bash
$env:SIDELENS_UI='1'
$env:SIDELENS_RENDER='gpu'
$env:SIDELENS_H264_DECODE='1'
./target/release/sidelensd.exe --udp 27200
```

## 三个设计决策

### 决策 1：默认关闭

`SIDELENS_UI` 未设置时不建窗口。理由：

1. 第三十九到五十二轮的所有延迟数字都是「无 UI」下测的，默认开会让那些
   数字失去可比性（多一个窗口合成器参与）
2. CI / 无桌面环境里建窗口会失败，默认关闭省掉一条降级分支

### 决策 2：关窗口不停服务

`pump()` 返回 `Closed` 时只置标志并打日志，**不退出主循环**。

daemon 是常驻接收服务：界面没了照样该收包。想停服务请 Ctrl+C。

这个决策有争议 —— 多数 GUI 程序关窗口就退出。但对「后台接收 + 可选界面」
这种形态，关窗口保留服务更符合直觉（用户可能只是不想看画面了）。

### 决策 3：面板文字每 2 秒更新，不是每帧

每帧（16ms）调 `SetWindowTextW` 会让窗口过程不断重绘，实测吃掉 2-3% CPU ——
而人眼根本看不清 60Hz 刷新的文字。

## 音频开关的语义

「启用音频」复选框**只跳过 `sink.write`**，不跳过解码与统计：

```rust
let audio_muted = panel.as_ref().is_some_and(|p| !p.audio_enabled());
if let Some(sink) = audio_sink.as_mut().filter(|_| !audio_muted) { ... }
```

用户关音频是为了**静音**，不是为了让 `audio_decoded` 变成 0 ——
后者会让人看不出音频链路是否健康。

## 集成须知（给 apps/ 下的真实客户端）

### 1. 必须嵌 comctl32 v6 的 manifest

没有 manifest 的进程加载的是 comctl32 **v5**，控件会退回 Win95 经典外观
（方块灰、无圆角、标题栏深蓝渐变）。

`sidelens-ui` 的 `build.rs` 只给**自己的 examples** 嵌了 manifest —— 库没有
链接阶段，管不到最终 exe。真实客户端要在自己的 `build.rs` 里做同样的事：

```rust
println!("cargo:rustc-link-arg-bins=/MANIFEST:EMBED");
println!("cargo:rustc-link-arg-bins=/MANIFESTINPUT:{path_str}");
```

**`/MANIFESTINPUT:` 的路径不能加引号** —— `cargo:rustc-link-arg` 是逐字传给
链接器的，加引号会被当成文件名的一部分（实测 `LNK1104`）。

### 2. 首帧闪烁：用 `new_hidden` + `show`

`MainWindow::new` 建完立刻显示。如果后面还要建十几个控件，用户会先看到
空窗口再看到控件一个个冒出来（实测 4-5ms 的闪烁）。正确顺序是
`new_hidden` → 建控件 → `show`。

### 3. 视频区要给渲染层

`MainWindow::video_rect` 返回**物理像素**的客户区矩形，每次 resize / DPI 变化
后都要重新取。`sidelens-render-gpu` 用它建 swap chain 的子窗口。

## 已知缺口

| 缺口 | 影响 |
| --- | --- |
| 视频按 1:1 显示不填满视频区 | 1736x928 区域放 1280x720 画面，左右有黑边（刻意不拉伸，便于排查裁剪问题） |
| 没有文本输入框 | 无法在界面里填目标地址/端口，仍需命令行 |
| 没有菜单/托盘 | 关闭后只能从任务管理器退出 |
| 无高对比度主题适配 | 系统开了高对比度模式时文字可能看不清 |
| 无 IME 特殊处理 | 中文输入法在某些布局下候选框位置可能偏 |
| 无滚动容器 | 控件多了放不下 |

## 与渲染层的集成（第五十四轮完成）

第五十三轮时 GPU 渲染器还是**独立顶层窗口**，会盖住面板。第五十四轮改成
**子窗口**模式，视频真正嵌在面板的视频区里。

```text
INFO 状态面板已创建 dpi=192 client=(1800, 1280)
INFO GPU 渲染器嵌入面板视频区（子窗口） video_x=32 video_y=192 video_w=1736 video_h=928
INFO GPU 渲染已启用 adapter="NVIDIA GeForce RTX 5070 Ti"
```

窗口层级（实测）：

```text
main 1826x1351
  子窗口 1736x928   ← GPU 渲染（正好等于 video_rect）
  子窗口 1720x48    ← 状态标签
  子窗口 1720x44 ×2 ← 延迟 / 视频信息标签
  子窗口 280x52     ← 复选框
```

界面内容（截图确认，全是真实数据）：

```text
+-- SideLens ----------------------------------------+
| ● 已连接  127.0.0.1:52838                          |
| 延迟 p50 21.26 ms  p95 24.10 ms  丢包 0.00%  抖动缓冲 14.0 ms |
| 视频 1280x720   351 帧   58.5 fps   0.0 Mbps        |
| +----------------------------------------------+  |
| |      （真实 H.264 解码画面，GPU 渲染）        |  |
| +----------------------------------------------+  |
| [x] 启用音频                                       |
+----------------------------------------------------+
```

### 集成的顺序约束

面板**必须先于**渲染器创建 —— 渲染器需要面板的 `hwnd()` 和 `video_rect()`。
第五十三轮时渲染器是独立窗口所以顺序无所谓，现在是硬约束。

### `StatusPanel::hwnd()`

返回 `isize` 而不是 `HWND`，让面板模块不依赖 `windows` crate 的类型 ——
面板本身只关心布局与文字。

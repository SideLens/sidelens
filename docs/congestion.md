# 拥塞控制与码率自适应

> 代码：[crates/sidelens-core/src/congestion.rs](../../crates/sidelens-core/src/congestion.rs)
> 测试：[tests/congestion.rs](../../crates/sidelens-core/tests/congestion.rs)、[tests/congestion_loop.rs](../../crates/sidelens-core/tests/congestion_loop.rs)
> 相关：[udp-nack-report.md](udp-nack-report.md)、[protocol.md](protocol.md)、[latency-budget.md](latency-budget.md)

这一层要回答一个问题：**在不知道链路带宽的前提下，每秒该往网络上灌多少比特。**

答案不是「尽量多」。灌多了，包在路由器的队列里排队，延迟从 20ms 涨到 800ms，
画面变成慢动作回放；灌少了，画面糊。所以真正要控制的是**排队延迟**，
带宽只是它的副产品。

---

## 1. 为什么实时视频不能用 TCP 式拥塞控制

### 1.1 两者优化的目标函数不同

TCP 的拥塞控制（Reno / CUBIC / BBR 之前的全部）优化的是**吞吐**，
约束条件是**不丢包**。它把路由器的缓冲区当成免费的仓库：
只要还没丢包，就继续加窗口。这个策略对文件传输是最优的 ——
下载慢 10% 没人看得出来，但丢一个包就要重传。

实时视频的目标函数完全相反：

| 目标 | 文件传输（TCP） | 实时视频（本模块） |
| --- | --- | --- |
| 首要指标 | 吞吐 / 完成时间 | 端到端延迟 |
| 可接受的延迟 | 秒级、分钟级 | < 150ms |
| 丢包的代价 | 重传，慢一点 | 花屏 / 卡顿 / 等关键帧 |
| 延迟的代价 | 几乎无感 | 直接毁掉可用性 |
| 缓冲区的作用 | 吸收抖动，提高吞吐 | **纯粹的延迟**，必须打空 |
| 拥塞信号 | 丢包 | 排队延迟增长 |

### 1.2 缓冲区膨胀：为什么「不丢包」是个陷阱

一个典型的家用路由器 / 4G 基站，出口队列有 200ms~2s 的缓冲
（bufferbloat）。TCP 会把这个队列填满并维持满 —— 因为在丢包之前，
它没有任何理由停手。

对视频这意味着：

```text
链路真实带宽 2 Mbps
发送端灌 3 Mbps
      ↓
队列以 1 Mbps 的速度积压
      ↓
1 秒后队列里有 1 Mb = 125 KB 的积压
      ↓
端到端延迟 += 125KB / 2Mbps = 500ms
```

**丢包率仍然是 0**。TCP 认为链路状态完美。用户看到的是 500ms 延迟的画面。

这就是为什么延迟必须当主信号：**它是唯一能在丢包发生之前看到问题的指标。**

### 1.3 两个信号的分工

| 信号 | 提前量 | 可靠性 | 噪声来源 | 在本模块中的角色 |
| --- | --- | --- | --- | --- |
| 排队延迟增长（梯度） | **早**：队列刚开始积压就能测到 | 中：受时钟漂移、采样抖动影响 | 调度抖动、WiFi 重传、时钟不同源 | 主信号（`DelayGrowth`） |
| 丢包率 | 晚：队列已经溢出才会丢 | 高：丢就是丢，没有歧义 | 链路误码、NACK 恢复干扰统计 | 兜底信号（`PacketLoss`） |

只用丢包的后果，用 [udp-nack-report.md](udp-nack-report.md) 的实测数据说明：
10% 包级丢包时，p95 延迟从 25.52ms 涨到 74.02ms，p99 到 150.21ms。
也就是说，**等到丢包率达到 10%，延迟已经炸了 3~6 倍**。
而丢包触发的降码率还要 1 个 RTT 才生效，用户已经卡了半秒。

反过来，只用延迟也不行：链路误码（WiFi 干扰、4G 弱信号）会造成丢包
但队列并不积压，此时梯度是 0，只看延迟会一路升码率直到彻底崩掉。
所以两个信号**同时监控，谁超标都降**，同时超标降得更狠（见 §4.3）。

## 2. 延迟梯度的数学原理

### 2.1 观测量

发送端在帧头打 `send_ts_us`（[protocol.md](protocol.md) §2 的偏移 20），
接收端在收包时记 `arrival_us`。定义第 i 个包的**单向延迟观测**：

```text
d_i = arrival_i - send_i
```

如果链路空闲，d_i 恒定（等于传播延迟 + 序列化延迟）。
如果队列在积压，d_i 会随时间线性增长 —— **增长率就是队列的填充速度**。

### 2.2 为什么用「延迟对发送时刻的斜率」而不是「延迟的绝对值」

绝对值没用：它包含传播延迟（光纤 5ms、4G 40ms、卫星 600ms），
你不知道其中多少是「正常的」，多少是「排队排出来的」。

但**斜率**是干净的：传播延迟是常数，求导后消失；排队延迟的导数就是
队列增长速率。所以判据是：

```text
slope = d(delay) / d(send_time) > τ
```

τ = `delay_gradient_threshold` = **0.015**（无量纲：ms 延迟 / ms 发送时间）。

物理含义：**发送端每往前推进 1 秒的发送时间，排队延迟增长 15ms。**
换成本模块的窗口尺度：20 个样本、20ms 间隔 = 380ms 跨度，
斜率刚好等于阈值时窗口内延迟增长 0.015 × 380 = 5.7ms。
这个量级刚好在测量噪声之上、在 bufferbloat 恶化之前，是实测调出来的。

### 2.3 最小二乘斜率

```rust
// congestion.rs:228
let nf = n as f64;
let mean_x = self.samples.iter().map(|(x, _)| *x as f64).sum::<f64>() / nf / 1000.0;
let mean_y = self.samples.iter().map(|(_, y)| *y as f64).sum::<f64>() / nf / 1000.0;

let mut cov = 0.0;
let mut var = 0.0;
for (x, y) in &self.samples {
    let dx = *x as f64 / 1000.0 - mean_x;
    let dy = *y as f64 / 1000.0 - mean_y;
    cov += dx * dy;
    var += dx * dx;
}
Some(cov / var)
```

即标准的 OLS 估计：

```text
        Σ (x_i - x̄)(y_i - ȳ)
beta = ---------------------
            Σ (x_i - x̄)²
```

其中 x_i 是**相对**发送时刻（相对第一个样本，微秒转毫秒），
y_i 是 d_i（微秒转毫秒）。

除以 1000 转成毫秒不是装饰：原始值以微秒计，60fps 跑 20 个样本后
x 的量级是 10^7，x² 是 10^14，在 f64 的 53 位尾数下
Σx² 的相对精度只剩 ~10^-2，而斜率阈值是 1.5×10^-2 ——
**不转单位会直接把判据淹没在浮点误差里**。

分母保护：`var < 1e-6` 时返回 `None`。发送时间跨度不足约 10ms 时，
分母趋零，斜率会爆成一个巨大的数，误判为拥塞。

### 2.4 为什么恒定时钟偏移不影响斜率

这是本模块最重要的一条性质，它让「两端时钟不同源」这个硬问题变得无关紧要。

设两端时钟差一个常数 C（可以是几秒，甚至几十秒）：

```text
y_i' = y_i + C
```

代入 OLS 分子：

```text
Σ (x_i - x̄)[(y_i + C) - (ȳ + C)] = Σ (x_i - x̄)(y_i - ȳ)
```

C 被**中心化**消掉了，分子完全不变；分母只含 x，也不变。所以
beta' = beta。

测试直接锁住了这条性质：

```rust
// tests/congestion.rs:34
fn clock_offset_does_not_affect_slope() {
    // 两端时钟差 5 秒（5000ms），但延迟恒定 —— 斜率仍应为 0
    let mut a = CongestionController::default();
    feed_constant(&mut a, 20, 5_000_000, 1_000_000);   // 偏移 5 秒
    let mut b = CongestionController::default();
    feed_constant(&mut b, 20, 25_000, 1_000_000);       // 偏移 25ms

    let sa = a.slope().unwrap();
    let sb = b.slope().unwrap();
    assert!(sa.abs() < 1e-9 && sb.abs() < 1e-9, "偏移不应影响斜率：{sa} vs {sb}");
}
```

### 2.5 但漂移会污染斜率 —— 以及它到底有多严重

上面的推导要求 C **恒定**。真实晶振有频差：普通无源晶振 ±50ppm，
廉价模块 ±200ppm。50ppm 意味着每秒累积 50µs 的偏移。

漂移对斜率的贡献可以精确算出来。若时钟漂移率为 ρ（ppm × 10^-6），
则 y_i = y_i_true + ρ·x_i，于是：

```text
beta_measured = beta_true + ρ
```

即**漂移直接叠加到斜率上**，量级是 50 × 10^-6 = 5×10^-5。

对比阈值 τ = 1.5×10^-2：漂移的贡献比阈值低 **300 倍**。
即使 200ppm 的劣质晶振，也只有 75 倍余量。所以：

| 场景 | 是否需要 ClockSync 校正 |
| --- | --- |
| 判定「是否在排队」（斜率） | **不需要**。常数偏移被消掉，漂移比阈值低 2~3 个数量级 |
| 报告绝对单向延迟（日志、抖动缓冲目标） | **必须**。绝对值含偏移，不同源时数字毫无意义 |
| 计算 `Feedback.rtt_ms` | 建议。但当前实现只用它做日志 |

这正是 [udp_server.rs](../../apps/sidelensd/src/udp_server.rs) 里
`cc.add_delay_sample(f.send_ts_us, now)` 直接喂原始时间戳、不做
`ClockSync::to_local` 却仍然正确的原因。

> **与模块注释的一处措辞差异**：`congestion.rs` 的模块文档写「时间戳必须先用
> `ClockSync` 校正过」。更准确的说法是：**斜率不需要，绝对延迟需要**。
> 校正了当然更好（消除漂移的 5×10^-5 偏置），但没校正也不会导致误判 ——
> 上表的余量说明了这一点。

### 2.6 为什么是 `arrival - send` 而不是「到达间隔 - 发送间隔」

后者（GCC 早期实现用的 `delta_ms`）需要相邻两个包：

```text
Δ = (arrival_i - arrival_(i-1)) - (send_i - send_(i-1))
```

它的问题是**对单个包丢失极其敏感**：丢一个包，i-1 变成 i-2，
间隔翻倍，Δ 直接爆掉，产生一次假拥塞。

`arrival - send` 每对样本独立：丢包只是少一个样本，
剩下的样本仍然正确。这在 10% 丢包的弱网上是决定性的差别。

## 3. 为什么用最小二乘而不是首尾差值

最朴素的做法是拿窗口首尾两点算斜率：

```text
slope_naive = (d_n - d_0) / (t_n - t_0)
```

它只用 2 个样本，**丢弃了中间 18 个样本的全部信息**。后果是它对
首尾两个点上的噪声完全无免疫。

### 3.1 定量对比

设真实斜率 0，噪声 ε ~ N(0, σ²)，窗口 n = 20，跨度 T = 380ms。

**首尾差值**的方差：

```text
Var[slope_naive] = 2σ² / T²
```

**最小二乘**的方差（经典结论）：

```text
Var[beta] = σ² / Σ(x_i - x̄)²  ≈  12σ² / (n·T²)
```

两者比值：

```text
Var[naive] / Var[beta] ≈ n / 6 = 20 / 6 ≈ 3.3
```

**最小二乘的标准差只有首尾差值的 55%。** 这不是微调，是把判据的
信噪比提高了 1.8 倍 —— 在阈值 0.015 这种量级上，直接决定误报率。

### 3.2 离群点：真正的杀手

方差分析假设高斯噪声，但实时视频的噪声是**重尾**的：

| 噪声源 | 典型幅度 | 频率 |
| --- | --- | --- |
| OS 调度抖动 | 1~5ms | 每几百帧一次 |
| WiFi 重传（CSMA 退避） | 10~50ms | 干扰时成簇 |
| 接收端 GC / 页面缺页 | 10~100ms | 偶发 |
| NACK 重传包到达 | 1 RTT | 丢包时 |

一个 +50ms 的离群点落在**最后一个样本**上时：

```text
naive:  slope = 50ms / 380ms = 0.132   ← 阈值的 8.8 倍，必然误判拥塞
        → 码率乘 0.85，一次白降 15%
```

同样的离群点对最小二乘的影响：它在 20 个点里只有一个，且 x_i - x̄
最大也只有 T/2，杠杆被摊薄。数值上，单个 +50ms 点对 beta 的贡献约为：

```text
Δbeta = (x_k - x̄)·50 / Σ(x_i-x̄)²  ≈  6·50 / (n·T) = 300 / (20×380) ≈ 0.039
```

仍然超过阈值 —— 但注意这是**最坏情况**（离群点恰在端点、且幅度 50ms）。
平均而言杠杆是 1/n 而不是 1/2。实测中这个差别体现在：
首尾差值版本在 WiFi 环境下几乎每个窗口都误报，最小二乘版本能稳定工作。

### 3.3 代价

最小二乘要遍历窗口两次（求均值、求协方差），O(n)，n = 20。
单次约 200ns。相对于 20ms 的决策周期可以忽略。

**取舍**：花 200ns 换 3.3 倍的方差改善和数量级的离群点鲁棒性。
没有任何理由选首尾差值。

## 4. AIMD 的两处调整

经典 AIMD（Additive Increase, Multiplicative Decrease）：
每个 RTT 加一个 MSS，检测到丢包就乘 0.5。本模块保留骨架，改了两个系数。

### 4.1 乘性减用 0.85 而不是 0.5

**为什么 TCP 用 0.5**：公平性。多条流共享瓶颈时，乘 0.5 能让
新流在几个 RTT 内收敛到公平份额（Chiu-Jain 的向量图证明）。
代价是每次拥塞吞吐腰斩。

**为什么这里不能用 0.5**：

1. **只有一条流**。公平性收敛根本不在考虑范围内 —— SideLens 是
   点对点单流，没有竞争。
2. **0.5 会造成可见的画质断崖**。1.6Mbps → 800kbps 意味着编码器
   要么把 QP 拉高一大截（糊），要么丢帧（卡）。用户对这一下的感知非常明显。
3. **过载通常只是短暂排队**。本模块的主信号是延迟梯度，它在队列刚开始
   积压时就触发 —— 此时链路只超了百分之十几，降 15% 就够了。
   降 50% 是过度反应。

**为什么是 0.85 而不是 0.95**：0.95 的单次降幅太小，需要 10 次以上
才能清空一个已经积压 100ms 的队列，而这期间延迟一直在涨。
0.85 对应「每次决策砍掉 15%」，配合 300ms 保持期，能在 2~3 个决策内
把队列打空。

| 系数 | 单次降幅 | 清空 100ms 积压所需次数 | 画质冲击 |
| --- | --- | --- | --- |
| 0.5（TCP） | 50% | 1~2 | 断崖 |
| **0.85（本实现）** | **15%** | **2~3** | 轻微 |
| 0.95 | 5% | 8~10 | 无，但延迟持续劣化 |

### 4.2 加性增每秒 8% 而不是每 RTT 翻倍

**为什么 TCP 是「每 RTT +1 MSS」**：这是「加性」的定义，保证多流公平
且收敛。它在时间上是**线性**的（每秒增长与 RTT 成反比）。

**为什么这里用百分比**：视频码率的合理范围跨两个数量级（200kbps~8Mbps）。
线性增长（比如每秒 +100kbps）在 200kbps 时是 50%/s（太快，立刻撞墙），
在 8Mbps 时是 1.25%/s（太慢，永远爬不上去）。百分比增长在
**任何码率下都是同一个相对速度**，这才是自适应的正确形态。

**为什么是 8%/s 而不是更快**：

码率过冲的代价是**非对称**的：

| 方向 | 代价 | 恢复时间 |
| --- | --- | --- |
| 升太快，撞墙 | 延迟瞬间 +200ms，一次降码率，画质断崖 | 数秒（见 §7） |
| 升太慢 | 画面比链路允许的略糊 | 无，只是不够好 |

在「糊一点」和「卡一下」之间，实时视频必须选前者。8%/s 意味着
从 1.5Mbps 爬到 3Mbps 需要 ln(2)/0.08 = 8.7 秒 —— 慢，但用户只会觉得
「刚开始有点糊」，不会觉得「卡」。

**绝对值上限**：`max_increase_step_bps = 100_000`。防止在高码率时
单步增量过大（8Mbps × 8% × 1s = 640kbps 一步，可能直接打爆队列）。
这个上限在 20ms 决策周期下不生效（8M × 8% × 0.02 = 12.8k），
但在 2 秒的实际上报周期下**会**生效（见 §10.1）。

### 4.3 叠加惩罚

```rust
// congestion.rs:401
let mut factor = self.config.decrease_factor;      // 0.85
if sig == CongestionSignal::Both {
    factor *= 0.9;                                  // 0.765
}
if fb.loss_ratio > self.config.loss_high_threshold {
    factor *= 0.9;                                  // 0.6885
}
```

| 情形 | 系数 | 单次降幅 |
| --- | --- | --- |
| 只有延迟梯度 | 0.85 | 15% |
| 只有丢包 | 0.85 | 15% |
| 延迟 + 丢包同时 | 0.765 | 23.5% |
| 延迟 + 丢包 > 20% | 0.6885 | 31.2% |

逻辑：**两个独立信号同时报警，说明不是测量噪声**。单一信号可能是
时钟抖动或一次误码；两者同时出现几乎必然是真实的链路过载，
此时犹豫的代价比多降一点大得多。

## 5. 保持期（hold）的作用

```rust
// congestion.rs:430
self.hold_until_us = now_us.saturating_add(self.config.hold_ms * 1000);  // 300ms
```

保持期内 `update` 直接返回 `RateState::Hold` / `Reason::Holding`，
码率一动不动 —— **即使网络看起来已经完全恢复**。

### 5.1 为什么必须有

没有保持期时，降完的下一个决策周期（20ms 后）如果梯度回到 0，
控制器立刻开始加性增。问题在于：

```text
t=0    梯度超阈值 → 降 15%，码率 1.6M → 1.36M
t=20ms 队列还没排空，但梯度暂时回落（窗口里混着老样本）→ 开始升
t=40ms 升回 1.4M，队列再次积压
t=60ms 梯度又超阈值 → 再降 15%
       ...
```

这就是**锯齿（sawtooth）**：码率在瓶颈附近来回抖，延迟一直降不下来。
更糟的是每次抖动都触发一次编码器重配置（QP 跳变），画质持续不稳。

保持期的本质是给**反馈回路一个死区**：降完之后，强制等待一个
超过「队列排空时间」的窗口，再重新评估。

### 5.2 为什么是 300ms

这个值要满足三个约束：

| 约束 | 边界 | 理由 |
| --- | --- | --- |
| 必须 > 队列排空时间 | ~100ms | 一个 200ms 深的缓冲区在 15% 降幅后需要约 100ms 排空 |
| 必须 > 一个决策周期的若干倍 | ~100ms | 否则反馈还没回来就又决策了 |
| 不能太长 | < 1s | 网络真的变好时，用户要等太久才看到画质恢复 |

300ms 是实测折中：足以让 200ms 的队列排空（实测降码率后延迟
在 150~250ms 内回落到基线），又不会让恢复期显得漫长。

### 5.3 保持期与丢包路径共用

注意保持期在**任何**降码率路径上都会设置（延迟、丢包、两者），
因为它的目的不是「响应延迟」，而是「防止在同一个瓶颈上反复撞墙」。

## 6. 码率下限与分辨率降级

### 6.1 为什么要有下限

`min_bitrate_bps = 200_000`（200kbps）。低于这个值，控制器**不再降**，
而是返回 `Reason::AtFloor`。

理由：码率和画质的关系不是线性的，在某个点以下会**断崖式崩塌**。
用「每像素比特数」（bits per pixel, bpp）衡量最清楚：

| 分辨率 | 30fps 像素率 | @200kbps | @400kbps | @800kbps | @1.5Mbps |
| --- | --- | --- | --- | --- | --- |
| 720p (1280×720) | 27.6 Mpx/s | **0.0072** | 0.0145 | 0.0289 | 0.0543 |
| 540p (960×540) | 15.6 Mpx/s | 0.0129 | 0.0257 | 0.0514 | 0.0965 |
| 360p (640×360) | 6.9 Mpx/s | 0.0289 | 0.0579 | 0.1157 | 0.2170 |
| 180p (320×180) | 1.7 Mpx/s | 0.1157 | 0.2315 | 0.4630 | 0.8681 |

经验值：H.264 在 **0.05~0.1 bpp** 之间画质可接受，低于 **0.02 bpp**
开始出现明显的块效应和振铃，低于 **0.01 bpp** 基本是色块。

看第一行：**720p @ 200kbps = 0.0072 bpp，已经在「色块」区间**。
同样 200kbps 给 360p 是 0.0289 bpp —— 4 倍的信息密度，画面明显更清楚。

### 6.2 所以该降分辨率，而不是死压 720p

这是编码器层面的一个反直觉结论：**在低码率下，降分辨率比降质量更划算。**

原因在于压缩的本质是去除冗余。空间冗余的去除效率随分辨率下降而提高
（相邻像素更相关），而量化误差在高分辨率下会变成可见的块边界。

```text
200kbps + 720p：编码器被迫用 QP≈45，8×8 块全部糊成一片，边缘锯齿
200kbps + 360p：QP≈28，细节保留，只是整体不锐利
```

用户对「整体不锐利」的容忍度远高于「满脸马赛克」。

### 6.3 实现

```rust
// congestion.rs:518
pub fn resolution_hint(&self) -> Option<(u32, u32)> {
    if self.target_bps > self.config.min_bitrate_bps * 2.0 {   // > 400kbps
        return None;                                            // 不用降
    }
    Some(if self.target_bps <= self.config.min_bitrate_bps * 1.2 {  // ≤ 240kbps
        (320, 180)
    } else {
        (640, 360)
    })
}
```

| 目标码率 | 建议分辨率 | 对应 bpp | 判据 |
| --- | --- | --- | --- |
| > 400kbps | `None`（保持原分辨率） | ≥ 0.0145 @720p | 还撑得住 |
| 240~400kbps | 640×360 | 0.035~0.058 | 720p 已经不够，降一档 |
| ≤ 240kbps | 320×180 | 0.116~0.139 | 逼近下限，降到最低档 |

阈值取 `min × 2.0` 和 `min × 1.2` 而不是写死 400000/240000，
是为了让下限可配置时行为自动跟随。测试
`resolution_hint_appears_near_floor` 锁住了「触底必须给建议」这条。

> **注意**：`resolution_hint` 只是**建议**。真正的分辨率切换由编码器层
> 执行（需要重建编码器、发关键帧），不在本模块职责内。这是有意的分层：
> 控制器只输出「该用多少带宽」，不碰编码器状态。

## 7. 一个真实的振荡陷阱

这是本轮实测发现的问题。它不是设计时的疏忽，而是**两个独立缺陷叠加**
产生的复合故障 —— 单独看每一个都不致命，合在一起让链路在拥塞后
瘫痪 26 秒。

### 7.1 实测日志

模拟条件：50 步正常网络（每步 20ms，共 1 秒）→ 10 步延迟持续增长
（每步 +10ms 额外延迟）→ 40 步恢复（延迟回到恒定）。

```text
  恢复3: target=200000 (触底)

  恢复39: target=206498                    ← 26 秒才从 200k 回到 206k
```

### 7.2 问题一：滞后过冲

**现象**：拥塞在第 10 步（拥塞9）结束，但控制器一直降到 恢复3 才触底 ——
**多降了 4 次**，从 377k 一路砸到 200k。整段下来共降了 13 次
（0.85^13 ≈ 0.12），把 1.62Mbps 砸到地板。

**根因**：延迟梯度窗口按**样本数**淘汰（`trend_window = 20`），
不是按时间。拥塞期塞进去的 10 个陡峭样本，要在恢复期被
**一个一个**顶出去 —— 每来一个干净样本，才淘汰一个脏样本。

看恢复期的斜率序列就明白了：

| 恢复步 | slope | 窗口里还剩几个脏样本 | 判定 |
| --- | --- | --- | --- |
| 恢复0 | 0.2274 | ~10 | 降 |
| 恢复1 | 0.1861 | ~9 | 降 |
| 恢复2 | 0.1447 | ~8 | 降 |
| 恢复3 | 0.1034 | ~7 | 降（此时触底） |
| 恢复4 | 0.0620 | ~6 | 降（已在地板，无效） |
| 恢复5 | 0.0207 | ~5 | 降（无效） |
| 恢复10 | -0.1782 | 0 | 不降 |
| 恢复15 | -0.2008 | 0 | 不降 |

斜率**线性衰减**，因为每步只淘汰一个脏样本。前 6 步都在阈值之上，
其中 4 步造成了真实的降码率。

**更微妙的一点**：恢复后期斜率变成**大负数**（-0.18、-0.20）。
这不是「延迟在下降」，而是窗口里同时装着拥塞期的高延迟样本和恢复后的
低延迟样本，两者的落差被拟合成了陡峭的负斜率。负斜率不会误判拥塞
（-0.18 < 0.015），但它说明**此时估计量已经失去物理意义** ——
窗口跨越了两个不同的链路状态。

### 7.3 问题二：恢复太慢

**现象**：触底后从 200kbps 爬回 1.5Mbps 花了 26 秒（40 步 × 20ms 只
爬到 206498，即 800ms 涨了 3%）。

**根因**：加性增是「按当前码率的百分比」算的。在下限时：

```text
step = 200,000 × 0.08 × 0.02s = 320 bps/步 = 16 kbps/秒
```

按这个**初始速度**线性外推，回到 1.5Mbps 需要：

```text
(1,500,000 - 200,000) / 16,000 = 81 秒
```

实际是指数增长（每步 W ← W × 1.0016），精确解是：

```text
t = ln(1.5/0.2) / 0.08 = ln(7.5) / 0.08 = 25.2 秒
```

实测 26 秒，与指数解吻合。**两种算法给出的数字（81s 与 25s）都对，
只是描述的是不同的东西** —— 81s 是「如果速度不变」，25s 是「速度随码率增长」。
用户感知到的是后者：整整 26 秒画面都是糊的。

### 7.4 修复一：拥塞后清空窗口

```rust
// congestion.rs:419
// 关键：清空延迟窗口。
//
// 实测发现的振荡陷阱：窗口里留着拥塞期的样本时，网络已经恢复
// 但斜率仍为正，会连续降 4 次直到触底（200kbps），
// 然后再花几十秒才爬回来。
self.trend.clear();
```

**语义**：拥塞事件是一个**状态断点**。断点之前的延迟数据描述的是
「旧的链路状态」，对判断「现在是否还在恶化」没有价值 —— 甚至有害，
因为它会把「曾经涨过」误读成「还在涨」。

清空后，`trend_min_samples = 6` 保证至少积累 6 个新样本才重新判定，
这段时间正好覆盖保持期的前 120ms。

**效果**：同一次拥塞事件从降 13 次变成降 2 次。

| | 修复前 | 修复后 |
| --- | --- | --- |
| 拥塞期降码率次数 | 9 次（拥塞1~9） | 2 次（拥塞1、拥塞7） |
| 恢复期继续降 | 6 次决策，其中 **4 次真的降到了新低** | 0 次 |
| 最低点 | 200000（地板） | 1175816 |
| 一次拥塞的总降幅 | 0.85^13 ≈ **12%** | 0.85^2 ≈ **72%** |

修复后仍有 2 次降：`clear()` 只买到约 120ms 的干净期，如果拥塞
**仍在持续**（本例中延迟还在涨），6 个新样本进来后梯度会再次超阈值。
这是正确的行为 —— 延迟真的还在涨，就该继续降。区别在于：
修复前是「网络恢复了还在降」，修复后是「网络真在恶化才降」。

### 7.5 修复二：记住拥塞前码率，做上界探测

```rust
// congestion.rs:298
/// 上次拥塞前的码率（恢复期用来加速爬升）
pre_congestion_bps: f64,

// congestion.rs:413
if changed {
    // 记住「拥塞前跑到过多少」——恢复期用它做上界探测
    self.pre_congestion_bps = self.pre_congestion_bps.max(self.target_bps);
}

// congestion.rs:483
let regular_step = self.target_bps * self.config.increase_ratio_per_sec * dt_sec;
let recovery_step = if self.pre_congestion_bps > self.target_bps {
    // 每步补上 1/4 的差距，但不超过常规步子的 8 倍
    let gap = self.pre_congestion_bps - self.target_bps;
    (gap * 0.25).min(regular_step * 8.0)
} else {
    0.0
};
let step = regular_step.max(recovery_step).min(self.config.max_increase_step_bps);
```

三个设计点：

1. **`max()` 累积而不是覆盖**：`pre_congestion_bps` 取历史最大值。
   链路曾经跑到 1.6Mbps，这个事实不会因为后来降到 200kbps 而失效。
   它代表「这条链路至少有过这么多余量」。

2. **按差距比例逼近，而不是一次跳回**：`gap × 0.25` 每步补 25% 的差距，
   是指数逼近，离目标越近步子越小，天然收敛，不会过冲。

3. **但真正起作用的是那个 8 倍上限**。在下限时：
   - `gap × 0.25 = 1.42M × 0.25 = 355k`（巨大）
   - `regular × 8 = 200k × 0.08 × 0.02 × 8 = 2560`（小）
   - `min` 取 2560

   所以实际速度是**常规的 8 倍**，即 64%/s。理论恢复时间
   `t = ln(7.5) / 0.64 = 3.15 秒`，实测 3.5 秒回到拥塞前 95% ——
   **8.5 倍加速，与 8× 系数吻合。**

### 7.7 仍然存在的问题

修复解决了症状，但没有解决**结构性问题**。以下是已知的剩余缺陷。

#### (a) 窗口按样本数淘汰，滞后时间随帧率漂移

`trend_window = 20` 是**样本数**。窗口覆盖的时间跨度 = 20 × 帧间隔：

| 帧率 | 窗口时间跨度 | 拥塞后的滞后上限 |
| --- | --- | --- |
| 60 fps | 333 ms | 333 ms |
| 30 fps | 667 ms | 667 ms |
| 15 fps | 1.33 s | 1.33 s |
| 10 fps | 2.0 s | **2.0 s** |

**帧率越低（往往正是弱网时），滞后越严重** —— 这是个正反馈的坏设计。
`clear()` 掩盖了大部分场景，但如果一次拥塞后**只有部分**样本被清空
（比如两次拥塞间隔很近），残留仍然会拖慢判定。

**改进方向**：按时间淘汰，而不是按数量。

```rust
// 现在
if self.samples.len() == self.capacity { self.samples.pop_front(); }

// 改为：双重淘汰 —— 容量上限 + 时间上限
const WINDOW_SPAN_US: i64 = 300_000;   // 300ms
let newest_rel = self.samples.back().map(|(x, _)| *x).unwrap_or(0);
while let Some(&(rel, _)) = self.samples.front() {
    if newest_rel - rel > WINDOW_SPAN_US {
        self.samples.pop_front();
    } else {
        break;
    }
}
```

这样无论 10fps 还是 60fps，窗口覆盖的都是「最近 300ms」，
滞后上限恒定。代价是低帧率时样本数少（10fps 只有 3 个），
需要相应下调 `trend_min_samples`，否则判不出来 —— 这是一个真实的取舍。

#### (b) 恢复速度仍然是「固定倍率」，不是「上界探测」

当前的 8× 是**常数倍率**。它不知道上次是在哪里撞的墙：

- 如果上次拥塞发生在 1.62Mbps，8× 爬升会在 3.5 秒后**再次撞上同一堵墙**
  （虽然这次只降 15%，比之前温和）
- 如果链路容量其实已经涨到 4Mbps（比如 WiFi 换了信道），8× 又太慢

**改进方向：CUBIC 式凸增长。**

CUBIC 的核心是一个三次函数，让码率在接近上次拥塞点时**自动减速**：

```text
W(t) = C·(t - K)³ + W_max
K = cbrt( W_max·(1-β) / C )
```

其中 W_max 就是本模块已经有的 `pre_congestion_bps`，β = 0.85，
C ≈ 0.4（Mbps³/s）。

代入 W_max = 1.6 Mbps：

```text
K = cbrt(1.6 × 0.15 / 0.4) = cbrt(0.6) = 0.84 秒
```

行为对比：

| 阶段 | 当前（8× 指数） | CUBIC |
| --- | --- | --- |
| 刚降完（1.36M） | 慢（8× 起步） | **快**（三次项斜率大） |
| 接近 W_max（1.6M） | 一直快，直接冲过去 | **自动减速**（拐点附近导数趋零） |
| 超过 W_max | 继续 8× 直到撞墙 | **极慢探测**（凹段，max-probing） |
| 回到 1.6M 用时 | 3.15 s | **0.84 s** |

关键优势是**「接近已知上界时自动变慢」** —— 这正是「上界探测」该有的形状：
远的时候快，近的时候慢，撞了之后把新的上界记下来。

**更简单的替代**（如果不想引入三次函数）：两段式速度。

```rust
let ratio = self.target_bps / self.pre_congestion_bps;   // 当前 / 已知上界
let speed = if ratio < 0.85 {
    0.50          // 远离上界：50%/s，快速回填
} else {
    0.08          // 接近上界：退回常规速度，谨慎探测
};
```

实现只有 4 行，效果接近 CUBIC 的主要部分（快回填 + 慢探测），
代价是切换点处有一个速度突变（CUBIC 是连续曲线）。

#### (c) `pre_congestion_bps` 永不过期

它是 `max()` 累积的，永远不会衰减。如果链路从 WiFi 切到 4G
（容量从 20Mbps 掉到 5Mbps），`pre_congestion_bps` 仍然是 20Mbps，
恢复期会以 8× 的速度往 20Mbps 冲，反复撞墙。

**改进方向**：给这个值加时间衰减，或者在一段时间内没再达到过就折半：

```rust
// 每次成功升到 pre_congestion_bps 的 95% 以上时，把它再抬高一点（确认有效）
// 连续 N 次拥塞都没达到它时，把它降到实际达到的最高点
```

这本质上是把「单点上界」变成「滑动上界」，也就是 BBR 里 btl_bw 的窗口最大值
思路（BBR 用 10 个 RTT 的窗口最大值，然后按 0.75 衰减）。

## 8. 与已有模块的关系

拥塞控制不是孤立的。它的输入来自三个模块，输出流向编码器。

```text
                    ┌──────────────────────────────────────────┐
   RTT_PROBE/REPLY  │  sync::ClockSync                         │
   ────────────────>│  offset_us / to_local                    │
                    │  （绝对延迟用；斜率不需要，见 §2.5）      │
                    └───────────────┬──────────────────────────┘
                                    │ 绝对单向延迟
                                    ▼
   Video 帧 ────────> ┌──────────────────────────┐
   (send_ts_us, now)  │  congestion::DelayTrend  │
                      │  最小二乘斜率             │
                      └──────────┬───────────────┘
                                 │ slope
   NACK 缺片统计 ─────> ┌─────────▼───────────────┐
   (帧级 → 包级反解)   │  CongestionController   │──> Decision{target_bps}
                      │  AIMD + hold + floor    │         │
                      └─────────────────────────┘         │ STATS 帧回传
                                 │                        ▼
   BitrateTracker ────> 实际码率（诊断/对照）        发送端编码器
```

### 8.1 与 NACK 的关系：丢包率的口径陷阱

这是踩过两次的坑，[udp-nack-report.md](udp-nack-report.md) §2 有记录。

**第一次踩坑**：用「最终未恢复丢包率」喂控制器。5% 链路丢包时读数是 0.000 ——
因为 NACK 把丢的包全补回来了，一个没丢。控制器把拥塞链路误判为健康，
一路升码率直到彻底崩掉。

**第二次踩坑**：改用「曾经缺过分片的帧占比」。但这是**帧级**丢包率，
而 `loss_threshold = 0.10` 是按**包级**定的（业界惯例）。5% 包级丢包
经过 7 个分片后，帧级是：

```text
1 - 0.95^7 ≈ 30%
```

直接喂进去，控制器以为链路烂了 6 倍，一路压到地板。

**正确做法**是反解回包级：

```text
p_packet = 1 - (1 - P_frame)^(1/n)
```

其中 n 是每帧的分片数（从帧大小估算，`div_ceil(SAFE_MTU_PAYLOAD)`）。

```rust
// udp_server.rs:337
let avg_frags = (fragments_in_window as f64 / received_frames_in_window as f64).max(1.0);
let loss_ratio = if frame_loss <= 0.0 {
    0.0
} else if frame_loss >= 1.0 {
    1.0
} else {
    1.0 - (1.0 - frame_loss).powf(1.0 / avg_frags)
};
```

**教训**：拥塞控制要的是「链路当时的丢包率」（链路挤不挤），
不是「恢复机制成功后的残留丢包率」（我们的 NACK 好不好用）。
这两者在小丢包率下差一个数量级，直接决定控制器是否工作。

### 8.2 与 BitrateTracker 的关系：诊断与交叉验证

[BitrateTracker](../../crates/sidelens-codec/src/bitrate.rs) 统计**实际**发出的码率
（滑动窗口 + 指数平滑，区分含头/不含头）。

它与拥塞控制是**开环与闭环**的关系：

| | BitrateTracker | CongestionController |
| --- | --- | --- |
| 测的是什么 | 我已经发了多少 | 我还能发多少 |
| 方向 | 过去 → 现在 | 现在 → 未来 |
| 精度 | 高（就是字节数） | 低（估计） |
| 作用 | 诊断、告警、交叉验证 | 决策 |

交叉验证的价值：如果 `target_bps = 1.5M` 但 `bitrate_with_overhead_bps()` 长期
只有 800k，说明编码器跟不上目标（CPU 瓶颈或 QP 已到上限），
继续升码率没有意义 —— 这是将来做「编码器饱和检测」的入口。

注意 `bitrate_with_overhead_bps()` 才是真实带宽占用：每帧 32 字节协议头
（[protocol.md](protocol.md) §2），8KB 帧是 0.4% 开销，但 200 字节的音频帧
是 16% —— 在低码率下必须算进去。

### 8.3 与 ClockSync 的关系

见 §2.5 的详细分析。一句话总结：

- **斜率**：常数偏移被最小二乘中心化消掉，漂移贡献 ~5×10^-5
  比阈值低 300 倍 → 不需要同步
- **绝对延迟**：必须同步，否则数字含未知偏移，无法用于抖动缓冲目标值
  或任何面向用户的报告

### 8.4 与抖动缓冲的关系

[JitterBuffer](../../crates/sidelens-core/src/jitter.rs) 的目标延迟
（默认 20ms，可自适应到 200ms）与拥塞控制是**互补**的：

- 抖动缓冲吸收**短期**波动（毫秒级，乱序、调度抖动）
- 拥塞控制消除**长期**积压（百毫秒级，队列堆积）

两者不能互相替代：加大抖动缓冲能掩盖延迟抖动，但掩盖不了持续增长的队列 ——
那只会让延迟越积越多。反过来，降码率能清空队列，但对 5ms 的乱序无能为力。

```rust
// tests/congestion.rs:480
assert!(
```

### 9.7 集成测试：闭环链路模型（5 个函数）

```text
     ↓ 排队延迟 + 丢包

```

这层能抓到单元测试抓不到的问题：码率算对了但换算成帧大小后依然打爆链路、

## 10. 未做的事

明确列出当前实现的边界，避免后来者误以为已经完善。

### 10.1 决策频率与窗口长度不匹配（最严重）

[udp_server.rs](../../apps/sidelensd/src/udp_server.rs) 每 **2 秒**才调一次
`cc.update()`：

```rust
// udp_server.rs:321
if last_report.elapsed() >= report_every {   // report_every = Duration::from_secs(2)
    ...
    let decision = cc.update(&Feedback { loss_ratio, rtt_ms: p50 }, sidelens_proto::now_us());
}
```

但延迟窗口只覆盖 **333ms**（20 样本 × 60fps 的 16.7ms）。这意味着：

- 每次决策只看到最近 333ms 的样本
- 中间 1.67 秒的样本被反复覆盖，**从未参与任何决策**
- 一次持续 500ms 的拥塞，如果恰好落在两次 update 之间，**完全被忽略**

更麻烦的是 `dt_sec` 被 `clamp(0.001, 1.0)` 截到 1.0，所以每 2 秒的实际
增量是 8% 而不是 16%，**有效增速只有设计值的 1/2**。

**该做**：把 `update` 提到 100~200ms 一次（与反馈周期匹配），
或者把窗口按时间拉长到 ≥ 决策间隔。二者必须匹配，否则控制器是在
用 333ms 的视野做 2 秒一次的决定。

### 10.2 没有带宽探测（pacing / probe）

当前是**纯反应式**：只有延迟涨了才降，从来没有主动探测「还能不能更快」。
8%/s 的慢速爬升是一种隐式探测，但效率很低。

业界做法（GCC / BBR）会在稳定期插入**探测脉冲**：短暂地把码率提高 20%
并观察延迟响应，如果没反应就确认有余量，有反应就立刻回退。
这比 8%/s 的连续爬升快得多，而且不依赖「记住上次到过哪里」。

### 10.3 没有考虑编码器实际能力

`target_bps` 直接下发给编码器，但没有任何反馈回路确认编码器跟得上。
如果 CPU 吃紧，编码器可能只能输出 800kbps，此时控制器继续升到 1.5Mbps
只会让帧间隔变大（掉帧），而延迟信号不会报警 —— 因为网络确实没堵。

**该做**：把 `BitrateTracker` 的实际码率与 `target_bps` 对比，
持续偏离说明编码器饱和，应该停止升码率并考虑降分辨率。

### 10.4 分辨率建议是开环的

`resolution_hint()` 只返回建议，没有实现「切换分辨率」的完整流程：
需要重建编码器、强制关键帧、通知接收端重配抖动缓冲。这些都不在本模块内。

而且当前只有两档（320×180 / 640×360），没有 540p，切换时画质跳变明显。

### 10.5 没有多流协调

音频和视频共用一个 `target_bps`。实际应该保证音频优先
（音频只占 64~128kbps，但断了就是爆音），视频用剩余部分。
当前没有这个拆分。

### 10.6 没有公平性机制

如果将来支持多路视频（多摄像头、屏幕共享 + 摄像头），
当前的单流 AIMD 会让两路互相抢带宽，没有收敛到公平份额的机制。
经典 AIMD 的 0.5 系数正是为此设计的，改成 0.85 之后失去了这个性质。

### 10.7 参数没有自适应

`delay_gradient_threshold = 0.015`、`hold_ms = 300`、
`trend_window = 20` 都是常数。真实链路的噪声水平差异巨大
（有线 vs WiFi vs 4G），固定阈值必然在某些链路上误报、在另一些链路上迟钝。

GCC 的做法是**动态阈值**：用窗口内斜率的 MAD（中位数绝对偏差）
估计噪声水平，阈值取 k·MAD。这需要额外的统计量，当前没做。

### 10.8 测试全部是模拟

所有测试用的都是合成的时间序列和简化链路模型，**没有真实网络验证**。
[udp-nack-report.md](udp-nack-report.md) §7 列的「带宽受限：未测」仍然是现状。

已知的未验证场景：

| 场景 | 风险 |
| --- | --- |
| 真实 WiFi（有重传、有突发干扰） | 梯度噪声可能远超阈值，误报率未知 |
| 4G / 5G（带宽剧烈波动） | 8%/s 的爬升可能跟不上带宽变化 |
| 跨设备时钟（真实漂移） | §2.5 的分析基于 ppm 估算，未实测 |
| 链路容量突变（WiFi 换信道） | `pre_congestion_bps` 过期问题（§7.7c）会暴露 |
| 高帧率（120fps） | 窗口跨度只有 167ms，样本数可能不足 |

### 10.9 测试文件的两个小瑕疵

`congestion_loop.rs` 里 `zero_loss_keeps_increasing_until_ceiling` 和
`permanent_congestion_settles_at_floor` 各有一个重复的 `#[test]` 属性
（第 221–223 行、241–243 行），导致它们被编译并执行两次。
不影响正确性，但让「测试数量」这个数字失真（报告 7 个，实际 5 个函数）。

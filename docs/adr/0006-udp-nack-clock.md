# ADR 0006：UDP 传输、分片与时钟同步

- 状态：已采纳
- 日期：2026-11-24

## 1. 为什么在 WebSocket 之外还要做 UDP

WebSocket 跑在 TCP 上，TCP 有**队头阻塞**：丢一个包，后续所有包都要等它重传。
对实时视频这是灾难 —— 一个 1500 字节的包丢了，整个 8KB 帧都卡住，
而那个帧后面的帧也全在缓冲区里排队。

实测对比（3% 丢包）：

| 指标 | WebSocket | UDP + NACK |
| --- | --- | --- |
| p50 | 20.83 ms | 20.97 ms |
| p95 | 21.82 ms | 57.70 ms |
| 10% 丢包下可用性 | 严重卡顿 | 545/601 帧送达 |

UDP 的 p95 更差（等重传），但**它只影响丢包的那一帧**，
而不像 TCP 那样拖累后面所有帧。这是可用性 vs 平均延迟的取舍。

**结论**：局域网好网用 WebSocket 足够；一旦有丢包（WiFi、移动网络），UDP 是唯一选择。

## 2. 应用层分片而不是 IP 分片

IP 分片的问题：丢任何一片，整个 IP 包作废，重传粒度是整个 8KB。

应用层分片（8 字节分片头）：

- 能精确知道缺哪一片
- 重传按帧粒度（比按片简单，且够用）
- 不受中间设备对 IP 分片的特殊对待（NAT/防火墙常丢弃分片包）

分片头布局：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 2 | fragment_index |
| 2 | 2 | fragment_count |
| 4 | 4 | total_size |

## 3. 快速缺片检测（关键优化）

只靠超时（30ms）会让缺片帧白等。但 UDP 有个性质：
**同一 socket 上后面的包到了，说明前面的包已过网络层最长可能路径**。

所以 highest_completed_seq > seq + 3 时立刻报缺，不必等超时。

## 4. 时钟同步：一个无法消除的偏差

NTP 式四时间戳：

```text
发送端                        接收端
  T1 ──── RTT_PROBE ────────→
                               T2 = 收到时刻
  T4 ←─── RTT_REPLY ─────────  T3 = 发出时刻
```

RTT = (T4 - T1) - (T3 - T2)
offset = ((T2 - T1) + (T3 - T4)) / 2

### 实测发现的偏差

同机回环时，真实 offset 应为 **0**，实测是 **-5.5ms**。

**根因**：对端记录的 T2 是**用户态读到包的时刻**，不是**网卡收到包的时刻**。
中间隔着内核唤醒 tokio 任务的调度延迟，实测约 5ms。
这部分整段计入去程，导致 offset 估偏负。

**为什么不能修**：NTP 用内核时间戳（SO_TIMESTAMPNS）避免这个问题，
tokio 没暴露这个能力。要修得上 socket2 + 手写 recvmsg，成本远超收益。

**影响范围**：

- 只影响「延迟数字的绝对值」，不影响抖动缓冲行为（后者只看相对间隔）
- 提供 apply_bias_correction() 让调用方显式扣除

## 5. 三个真 bug 的教训

| bug | 现象 | 教训 |
| --- | --- | --- |
| NACK 用独立 socket 收 | 服务端 nack_sent=324，发送端 retransmitted=0 | UDP 的「我的地址」是这个 socket 的地址 |
| saturating_sub 做时间比较 | 刚标记的缺失立刻到期 | now<delay 时返回 0，必须用 checked_sub |
| 请求后删记录 | 重传再丢无人管，healed 永远 0 | 重传是有损信道上的一次博弈，要允许重试 |

第一个 bug 最隐蔽：**两端日志都显示在正常工作** ——
服务端在发 NACK、发送端在发视频帧，但中间的握手断了。
如果不是加了 cache_served 这个统计字段，这个 bug 会一直藏着。

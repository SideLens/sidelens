## 5. 数据口径（读表前必看）

接收端日志里的字段有**三种口径**，混用会得到完全错误的数字：

| 口径 | 字段 | 本工具怎么取 |
| --- | --- | --- |
| 进程累计 | `frames` `nack_seqs` `healed` `expired` `fec_recovered` `av_synced` | 取最大值 |
| 2 秒窗口 | `loss` `rx_fps` `kbps` `fec_reds` `avg_frags` | 跳过首尾两窗后取中位数 |
| 4000 样本滑动窗 | `net_ms` `playable_ms` `hold_ms` `audio_depth_ms` | 取最后一行 |

**为什么窗口类要跳过首尾**：首窗是启动斜坡（FEC 配置还没协商完、抖动缓冲刚建），
末窗是残窗（发送端已经退出，窗口里只剩半截帧）。实测末窗的 `rx_fps` 会从 30 掉到 11，
直接取最后一行会让每组都「看起来跑不满帧率」。

**为什么 `frames` 会大于发送端 `sent`**：接收端的 `frames_in` 同时统计
`FrameType::Video` 与 `FrameType::Retransmit`（见 `udp_server.rs` 的
`FrameType::Video | FrameType::Retransmit =>` 分支），而重传是同一个 seq 的再次到达。
所以 `frames` 是**到达帧次**而不是**去重后的帧数**，`rx_fps` 同理可能超过发送帧率。
丢包越重、重传越多，这个差值越大 —— 它本身是个有用信号（= 重传量），
但**不要**拿 `frames` 直接和 `sent` 对比来判断丢帧。

**`mbps` 的来源**：`发送结束` 那行没有 `mbps` 字段，它只在每 5 秒的 `发送中` 里。
所以取最后一条 `发送中`；发送时长不足 5 秒时退化为 `(fec_data_bytes + fec_red_bytes) / elapsed`，
两者口径不同（后者含冗余字节），表里不混用。

## 6. 已知问题（踩过的坑）

### 6.1 `Start-Process -RedirectStandardOutput` 会把「被外部杀」伪装成「程序早退」

第一版用 `Start-Process -RedirectStandardOutput $f -PassThru -NoNewWindow` 起进程，
跑矩阵时偶发**发送端 ExitCode=-1 且日志只有 1 行**（停在「UDP 模式」），
而同样参数手工跑完全正常。两个问题叠在一起：

| 现象 | 真正原因 |
| --- | --- |
| `ExitCode = -1` | `TerminateProcess(h, -1)` 的特征值。**不是 Rust 的退出码**：panic 返回 101、`Err` 返回 1，绝不会是 -1。看到 -1 就说明进程被**外部强制结束**（同机其他自动化在批量 `Get-Process sidelensd,sidelenssend \| Stop-Process -Force`；本仓库是多 agent 并行开发，这个风险是真实的） |
| 日志只剩 1 行 | `Start-Process` 的重定向由 PowerShell 另起一条复制线程搬输出，进程被杀时这条线程可能还没刷完 |

**现在的做法**：自己建 `System.Diagnostics.Process`，`RedirectStandardOutput = true` +
`ReadToEndAsync()` 由本进程直接收流，退出后拿到的一定是完整内容；日志仍落盘可回看。

**再加一次自愈重试**：只有「ExitCode=-1 且没有「发送结束」」才重试。
这个判据是安全的 —— 真正的程序缺陷会稳定返回 101，重试不会变绿，照样记 failed。
重试过的配置在 JSON 的 `retries` 字段里有记录。

### 6.2 解析器用相对路径会静默读不到文件

PowerShell 的 `Get-Location` 和进程 CWD 是**两个东西**。
用相对路径调 `[System.IO.File]::ReadAllLines()` 会按**进程 CWD** 解析，
读不到时抛 `IOException`，被 `catch` 吞成空日志 —— 表现是「49 个字段全缺失」，
而不是「路径错了」，排查时极易误判成正则写错。
现在解析器入口统一 `Resolve-Path` 转绝对路径，并单独输出 `IOErrors` 字段。

### 6.3 端口与进程残留

- 每个配置用不同端口（9100 起递增）。daemon 在端口被占时会**自动 +1 上移最多 20 次**
  （`crates/sidelens-transport/src/udp.rs` 的 `bind`），所以「传了 9100」不等于「它在听 9100」。
  脚本从日志读回真实端口再拼发送端目标，端口上移会在报告里留痕。
- 脚本**开头和结尾**都执行 `Get-Process sidelensd,sidelenssend \| Stop-Process -Force`。
- 每个配置起**全新 daemon**：接收端 `frames`/`nack_seqs`/`expired`/`fec_recovered` 是进程累计值，
  复用 daemon 会让后一组把前一组算进去。

### 6.4 日志没写完就开始解析

daemon 每 2 秒打一行统计。发送端退出后**再等 2.4 秒**才杀 daemon，
保证最后一个窗口落盘；那个窗口是残窗（只剩半截帧），解析器会跳过它。

### 6.5 本环境的测量噪声

同机回环、单机跑、多 agent 并行 —— 抖动主要来自调度而不是网络。
表中 p99 与 `net_ms` 的高位明显受此影响，**不要**把它们当作链路质量的绝对值，
只用同一次运行内的**相对比较**。

### 7.1 唯一对不上的数字：UDP 0% 丢包 p50 = 23.06 ms

这个数字在 `progress.md` 的「关键实测数字」表和 `udp-nack-report.md` 里都出现过，
并被用来论证「UDP 版 p50 比 WebSocket 高 2.2ms，是分片带来的额外遍历与拷贝」。
**本次三次独立复测都是 20.93 / 20.96 / 20.96 ms，稳定复现不出 23.06。**

排除了三种解释：

| 可能原因 | 验证 | 结论 |
| --- | --- | --- |
| 取错统计窗口（首窗斜坡偏高） | 逐窗查：20.95/20.97/20.96/20.97/20.99/20.99，全程平坦 | 排除 |
| 抖动缓冲 target 被自适应抬高 | 六行日志 `target_ms` 全是 20.0 | 排除 |
| 机器负载/环境不同 | 同机、同二进制、同一时段连续跑 | 排除 |

**最可能的解释**：23.06 那轮测量里 `playable` 的滑动窗口还残留启动期样本，
或当时跑的是更早版本的二进制（`target_ms` / 出队节拍改过）。
无法回溯确认，但**可以确定：按当前代码复现不出 23.06**。

**实质影响**：`udp-nack-report.md` 的结论「UDP p50 比 WebSocket 高 2.2ms，是分片开销」**不成立**。
实测 UDP 20.96 vs WebSocket 20.95 —— **两者 p50 上没有可测量的差异**。
分片确实有开销，但它落在 `net_ms`（0.2ms 量级）里，
而 p50 由 20ms 抖动缓冲主导，这点开销被完全淹没。
正确说法：**UDP 的代价不在 p50，而在 p95**（丢包时等重传，3% 丢包 p95 从 22ms 跳到 58ms）。

### 7.2 顺带发现：`frames` 与 `sent` 不可直接比

0% 丢包时 `frames=582` 而 `sent=600`，看起来像丢了 18 帧。
实际上 `frames` 是**到达帧次**且只在窗口内累加，而 `sent` 是发送端总数 ——
窗口边界不同。再叠加 `Retransmit` 也计入 `frames`（见第 5 节），
这个对比没有意义。判断丢帧应看 `loss` / `frame_loss`。

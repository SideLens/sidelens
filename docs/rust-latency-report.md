# Rust 核心端到端实测报告

> 测试日期：2026-11-24
> 环境：Windows，同机回环（127.0.0.1），WebSocket over TCP
> 配置：60 fps，每帧 8192 字节，持续 10 秒

## 1. 结论

| 指标 | 实测 p50 | 实测 p95 | 说明 |
| --- | --- | --- | --- |
| 网络单程延迟 | 0.22 ms | 0.32 ms | 编码时刻 → 服务端收到 |
| 可播放延迟 | 20.83 ms | 21.82 ms | 编码时刻 → 抖动缓冲判定可播 |
| 缓冲滞留时间 | 20.61 ms | 21.61 ms | 到达时刻 → 出队时刻 |
| 帧率 | 59.6 fps | — | 目标 60fps |
| 丢帧 | 0 | — | late=0 |
| 关键帧请求 | 0 | — | 缓冲从未溢出 |

**抖动缓冲目标 20ms，实测滞留 20.6ms，误差 0.6ms。** 说明缓冲调度精准到位。

## 2. 最关键的一次发现：Windows 定时器分辨率

第一版测出来是 **31ms**，比目标 20ms 多了 11ms。查了两轮才发现根因。

### 现象

```text
interval( 1ms)  实测 p50=15.620ms   <- 写 1ms，实际 15.6ms
interval( 2ms)  实测 p50=15.619ms
interval( 4ms)  实测 p50=15.623ms
interval(16ms)  实测 p50=15.656ms
```

**四个不同的间隔值，实测全是 15.6ms。** 这不是 tokio 的问题，
而是 Windows 的默认定时器分辨率就是 15.625ms（64Hz）。

### 影响

帧在抖动缓冲里到期后，还要等下一次 tick 才能被取走。
平均白等 **7.8ms**（半个 15.6ms），实测多出 11ms。

这部分延迟完全隐形：抖动缓冲自己报告 20ms，实际可播放 31ms。
如果没有单独统计 `hold_ms`，这个 bug 会一直藏着。

### 修复

`timeBeginPeriod(1)` 把系统分辨率提到 1ms：

```text
=== timeBeginPeriod(1) 之后 ===
interval( 1ms)  p50= 1.518ms   <- 从 15.6ms 降到 1.5ms
interval( 4ms)  p50= 4.502ms
interval(16ms)  p50=15.762ms
```

修复后延迟从 31ms 降到 20.8ms，**减少了 10ms**。

### 代价

`timeBeginPeriod` 影响**全系统**（其他进程的 sleep 也变精确），
会让功耗略升。所以实现成 RAII 守卫（`HighResTimer`），Drop 时自动还原。

### 为什么不干脆用 16ms tick

因为 tick 粒度决定“震动缓冲之外的额外延迟”：

| tick | 额外延迟（平均） | CPU 唤醒 |
| --- | --- | --- |
| 16ms | 8ms | 62 次/秒 |
| 4ms | 2ms | 250 次/秒 |
| 1ms | 0.5ms | 1000 次/秒 |

1ms 时 CPU 唤醒 1000 次/秒，对一个常驻服务来说可以接受（每次唤醒约 5us）。

## 3. 数据流与各段耗时

```text
发送端                            服务端
-------------------------------------------------
now_us() ---- 打 PTS/sendTs --+
                              |
  encode_frame()     ~60ns    |
                              |
  WebSocket 发送              |
                              v
                              收到 -> 解码 104ns
                                   | net_ms ~ 0.22ms
                                   v
                              jb.push() 入队
                                   |
                              <- 等 target_ms 20ms ->
                                   |
                              ticker 发现到期（1ms 粒度）
                                   | hold_ms ~ 20.61ms
                                   v
                              出队 -> 交给渲染/虚拟摄像头
```

各段相加：0.22（网络）+ 20.0（缓冲）+ 0.6（tick 粒度）= **20.82ms**，与实测 20.83ms 吻合。

## 4. 实测方法

```bash
# 终端 1：服务端
./target/release/sidelensd.exe 27100

# 终端 2：发送端（60fps，8KB/帧，跑 10 秒）
./target/release/sidelenssend.exe ws://127.0.0.1:27100 60 8192 10
```

服务端每 2 秒打印一次统计：

```text
统计 fps=60 frames=597 bytes=4909808 net_ms="0.22/0.32/0.42"
     playable_ms="20.83/21.82" hold_ms="20.61/21.61"
     jitter=0 target_ms="20.0" late=0 kf_req=0
```

字段含义：

- `net_ms`：p50/p95/p99 网络单程延迟
- `playable_ms`：p50/p95 可播放延迟（编码 → 出队）
- `hold_ms`：p50/p95 缓冲滞留（到达 → 出队）
- `jitter`：当前队列深度（帧数）
- `target_ms`：当前目标延迟
- `late`：迟到丢弃的帧数
- `kf_req`：请求关键帧的次数

## 5. 这个数字意味着什么

**20.83ms 是「我们这一侧」的延迟**，包含：

- [x] 协议打包与解析
- [x] 网络传输（回环）
- [x] 抖动缓冲
- [x] 出队调度

**不包含**：

- [ ] 相机曝光（60fps 时 16.7ms，物理下限）
- [ ] H.264 硬件编码（6-12ms）
- [ ] H.264 硬件解码（4-8ms）
- [ ] 虚拟摄像头注入 + 消费端应用渲染（33-150ms）

完整预算见 [latency-budget.md](latency-budget.md)。**工程可控部分是 20.8ms**，
加上编解码与采集后约 50-65ms，与最初的设计目标一致。

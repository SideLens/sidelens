# 加密层

> 状态：**已实现并通过 40 项测试**（39 集成 + 1 文档）。尚未接入 daemon。
>
> 代码：`crates/sidelens-crypto/`

## 为什么需要这一层

协议 v0/v1 的帧头里**没有任何认证字段**。任何人都能：

| 攻击 | 后果 | 现在的防护 |
| --- | --- | --- |
| 嗅探 | 看到摄像头画面与麦克风音频 | ChaCha20-Poly1305 加密载荷 |
| 篡改 `flags` | 把 P 帧标成关键帧，解码器从错位处开始解 | 帧头作为 AAD 参与认证 |
| 篡改 `seq` | 打乱重组与重放窗口 | 同上 |
| 篡改 `pts_us` | 音画同步被拉偏，或帧被判「迟到」丢弃 | 同上 |
| 重放旧帧 | 把「用户在电脑前」的旧画面循环播放 | `ReplayGuard` 位图窗口 |

手机把摄像头和麦克风共享给电脑，链路跑在同一段 WiFi 上 —— 这是最容易
被动嗅探的场景。没有加密层的「低延迟投屏」本质上是一个公开的摄像头。

## 三个设计约束（踩错就静默失效）

### 1. 加密必须在重传缓存**之上**

这是最容易做错的一处。发送端的重传路径会把**同一个 `seq` 的字节原样再发一遍**。

如果按「每发一次就加密一次」实现，同一个 `(key, nonce)` 会被用两次 ——
ChaCha20 是流密码，两次异或同一个密钥流会直接泄露两份明文的异或值。
**这是灾难性的，而且测试全绿、功能完全正常。**

正确做法：

```text
帧产生 → 加密一次 → 存入重传缓存（存的是密文）→ 首传
                                    ↓
                          NACK → 从缓存取密文原样重发
```

所以 `FrameSealer::seal_frame` 内部记录已封过的 `(stream_id, seq)`，
**重复封同一个 seq 直接返回 `CryptoError::NonceReuse`**。把「不该发生的事」
变成显式失败，而不是静默的 nonce 重用。

### 2. nonce 唯一性来自「每会话一把新密钥」

`seq` 是每路流从 0 开始的，发送端重启就回到 0。所以 nonce 不能只由 `seq` 决定。

解法：握手时双方各出 32 字节随机数，一起进 HKDF 的 salt。**新会话 = 新密钥**，
于是 `seq` 归零是安全的。

```text
salt = SHA256( "sidelens-v1 handshake"
             ‖ 发起方公钥 ‖ 发起方随机数
             ‖ 响应方公钥 ‖ 响应方随机数 )
```

按角色拼（发起方在前）而不是按字节序排序，是为了让**角色绑进密钥**：
两端角色搞反时 SAS 必然不一致，用户核对立刻发现。

### 3. 帧头必须「可见但被认证」

`seq` / `stream_id` / `flags` 是路由、重组、NACK 的依据，不能加密 ——
加密了这些字段，接收端在解密前就不知道该把包放进哪个流、要不要请求重传。

但它们作为 **AAD** 参与认证：看得见，改不了。

```text
明文帧 = [32B 帧头][载荷]
               ↓ seal_frame
密文帧 = [32B 帧头][密文载荷][16B 认证标签]
         └──── AAD ────┘
```

## 线格式

### nonce 的拼法（12 字节）

```text
偏移 0  4B  方向与流号   bit31 = 方向（0 = 发起方→响应方），bit0..15 = stream_id
偏移 4  4B  帧序号 seq（小端）
偏移 8  4B  全 0
```

后 4 字节留全 0 是**刻意留白**：将来若要加「同一 seq 的多个分片各自加密」，
这里就是现成的计数器。用满反而危险。

方向位是冗余的（两个方向用不同密钥），保留它是纵深防御：万一有人把两个方向
合并成一把密钥，这 1 bit 会让 nonce 立刻冲突，测试会红，而不是安静地重复。

### 加密后的帧长度

`payload_len` 字段（偏移 28）**必须**同步改成 `明文长度 + 16`，而且它同时是 AAD
的一部分。所以顺序是：

```text
1. 改 payload_len = 明文 + 16
2. 用改好的帧头当 AAD
3. 加密载荷，追加 16B 标签
```

反过来做（先加密再改长度）会让 AAD 与实际帧头不一致，接收端必然
`AuthenticationFailed` —— 而错误码看起来像「有人在攻击」，排查方向会被完全带偏。

## 分片与 MTU 的关系

```text
每片数据 = MAX_DATAGRAM(1200) - HEADER(32) - FRAG_HEADER(8) = 1160
分片数   = ceil(payload_len / 1160)
```

实测四档（`cargo run --release -p sidelens-crypto --example bench`）：

| 明文 | 密文 | 分片（前→后） |
| --- | --- | --- |
| 2048 B | 2064 B | 2 → 2 不变 |
| 8192 B | 8208 B | 8 → 8 不变 |
| 16384 B | 16400 B | 15 → 15 不变 |
| 65536 B | 65552 B | 57 → 57 不变 |

**加密只在「明文长度正好落在分片边界前 16 字节内」时才多一片**，
概率约 16/1160 ≈ 1.4%，对带宽影响可忽略。

## 性能实测

`cargo run --release -p sidelens-crypto --example bench`

| 帧大小 | 加密 | 解密 | 占 20ms 预算（加密） |
| --- | --- | --- | --- |
| 2 KB | 3.46 µs（605 MB/s） | 2.62 µs（793 MB/s） | 0.017% |
| 8 KB | 8.74 µs（943 MB/s） | 6.54 µs（1258 MB/s） | 0.044% |
| 16 KB | 15.55 µs（1056 MB/s） | 11.94 µs（1374 MB/s） | 0.078% |
| 64 KB | 58.23 µs（1126 MB/s） | 44.02 µs（1489 MB/s） | 0.291% |

**结论：加密不是延迟瓶颈。** 720p 典型帧只花 8.74 µs，占 20ms 延迟预算的
0.044%。即使关键帧 64KB 也只占 0.29%。

这推翻了一个常见的直觉（「加密会显著增加延迟，实时视频要谨慎」）——
在 1 GB/s 级的 ChaCha20 实现面前，视频码率（~1 MB/s）低了三个数量级。

## 重放防护

### 为什么必须按流分开计数

协议里视频是 `stream_id=0`、音频是 `stream_id=1`，两套 `seq` **各自从 0 累加**。
用一个窗口管所有流会出现：

```text
视频 seq=100 → 窗口 [0, 100]
音频 seq=3   → 3 < 100 - window，判为重放 → 音频全被丢掉
```

**实测症状**：音频一帧都进不了抖动缓冲，而日志只说「重放」，排查方向被完全带偏。
这和第十九轮「音频 seq 污染视频记账」是同一类错误的不同表现 ——
**凡是按 seq 记账的地方，都必须问一句「这个 seq 是哪个流的」**。

所以窗口是 `HashMap<stream_id, ReplayWindow>`。

### 窗口大小：1024

太小会误杀**正常的乱序包**。UDP 在 WiFi 上乱序 10-30 个包很常见，
NACK 重传更是可能晚到几百个 seq。1024 覆盖任何合理乱序，
内存只是一个 `[u64; 16]` 位图（128 字节/流）。

### u32 回绕

`seq` 是 u32，跑到 2^32 会回绕到 0。直接比大小会把回绕后的新包判成「过旧」。

用有符号差值比较：

```rust
let diff = seq.wrapping_sub(highest) as i32;
```

只要两个 seq 相差不到 2^31，差值符号就是正确的 —— 对实时媒体
（每秒几十到几百个包）来说，这个前提永远成立。

## 握手：X25519 + HKDF-SHA256

### 为什么不能直接用 ECDH 输出当密钥

裸的 ECDH 输出是曲线上的一个点坐标，**分布不是均匀随机的**，而且不同曲线的
输出长度不一样。标准做法是喂进 KDF 得到定长、均匀分布的密钥材料。

```text
shared = X25519(本端私钥, 对端公钥)
salt   = SHA256(transcript)
okm    = HKDF-SHA256(salt, shared, info="sidelens-v1 traffic keys", 64B)
         ├─ k_i2r (32B)  发起方 → 响应方
         └─ k_r2i (32B)  响应方 → 发起方
```

### 低阶点攻击必须显式拦

X25519 对**低阶公钥**（small-order point）会产生全零的共享密钥。
攻击者发一个低阶点，双方算出的「密钥」就是已知的，加密形同虚设。

`x25519-dalek` 的 `was_contributory()` 检测这一点（共享密钥全零即 false）。
必须在派生前检查，否则整条链路静默失效。

```rust
if !shared.was_contributory() {
    return Err(HandshakeError::LowOrderPoint);
}
```

注意：**对端实现没有 bug 时不可能触发这个条件**。触发了就是有人在攻击，
日志里要按安全事件对待，不是「兼容性问题」。

### SAS：抵御中间人的唯一手段

没有 PKI 时，密钥交换本身不认证对端 —— 中间人可以各连一头。
用户必须在两块屏幕上核对同一个 6 位数字：

```text
SAS = HKDF-SHA256(salt, shared, info="sidelens-v1 sas", 4B) mod 1_000_000
```

取模有极小偏置（2^32 不能被 10^6 整除，偏差约 1e-4），对 SAS 的用途
（攻击者要在用户核对前猜中）完全可以忽略 —— 猜中率仍是 1e-6 量级。

## 解密失败不区分原因

认证失败可能是因为：密钥不对、AAD 被改、密文被改。**对外只报一个错误**
（`CryptoError::AuthenticationFailed`）。区分它们等于给攻击者一个 oracle。

唯一的例外是重放，它在认证**之前**由 `ReplayGuard` 拦下，
因为重放检测不需要密钥。

## 接入 daemon 后抓到的三个真实 bug

这一节记录的是「加密层单测全绿、接进真实链路后立刻暴露」的问题。
三个都属于同一类：**加密是横切关注点，每个绕过它的路径都是漏洞**。

### 1. FEC 恢复的帧绕过了解密（最严重）

正常路径的解密在 `dg.completed` 之后，而 FEC 恢复走的是**另一条路** ——
分片由冗余包还原、直接喂给重组器，重组结果根本没经过那段代码。

**怎么发现的**：写了一个负面测试，两端故意用不同的 PSK。

```text
修复前：decrypt_failed=212  av_synced=14     ← 14 帧密文被当成明文播了
修复后：decrypt_failed=311  av_synced=0      ← 一帧都没漏过去
```

那 14 帧在画面上表现为周期性花屏，**频率与丢包率正相关** ——
极易被误判为「解码器问题」或「码率太高」。

修法：FEC 恢复路径也必须走「先重放检查、再解密」，判据与正常路径完全一致。
**两条路的判据不能有两套**，这是这次最该记住的一句。

### 2. FEC 恢复的关键帧丢了关键帧位

`DatagramPiece` 的 `flags` 在恢复路径里硬编码成 `FLAG_FRAGMENT`，
而重组器输出时做的是 `flags & !FLAG_FRAGMENT` —— 结果 flags = 0。

```text
关键帧丢了第 0 片 → FEC 恢复 → flags = FLAG_FRAGMENT
重组器输出 flags = 0（关键帧位没了）
抖动缓冲认为「不是关键帧」→ needs_keyframe 逻辑失效
```

表现是「丢包时灰屏直到下一个自然关键帧」，而日志里 `fec_recovered` 一切正常。

修法：`FragmentInfo` 加 `flags` 字段，`FecReceiver::frame_meta` 存三元组
`(pts_us, send_ts_us, flags)`，恢复时原样带回。`UdpDatagram` 也补了 `flags`。

**这个 bug 的教训**：FEC 恢复路径要还原的不只是「数据」，还有**帧的全部元数据**。
之前只想到时间戳（因为填 0 会被判迟到），漏了 flags（因为它不参与任何校验）。

### 3. 重放窗口对重传误杀（计数虚高，非功能 bug）

`replay_rejected` 稳定在 1-4 次/6 秒，而链路正常。

原因：NACK 重传会让同一个 `seq` 到达两次 —— 第一次进了窗口，第二次被判重复。
**这是重传的正常行为，不是攻击**。当前把它计入 `replay_rejected` 会让人误判。

正确做法（未做）：重放检查应该只在「**非重传**帧」上做，或者把
`FLAG_RETRANSMIT` 的帧单独放行。现在只是记在文档里，因为
「重传的帧被重放窗口拦住」在功能上等价于「重传失败」，影响很小。

## 与 FEC/NACK 的关系

三者不冲突，顺序是：

```text
发送：帧 → 加密 → 分片 → [FEC 冗余] → UDP
接收：UDP → [FEC 恢复] → 重组 → 重放检查 → 解密 → 抖动缓冲
```

**FEC 与重传都作用于密文**。这是加密层设计成「原地修改完整帧」而不是
「加密载荷返回新 Vec」的原因 —— 密文一旦产生就不会再变，可以被任意复制、
分片、XOR、缓存。

| 指标 | 值 | 说明 |

| `fec_overhead` | 27.5% | 与未加密时的 27.4% 基本相同（+16B/帧可忽略） |
| `audio_sent` | 301 | 音频也加密，节拍未受影响 |
| `playable_ms` | 20.89/21.96 | **p50 延迟与未加密时（20.94/21.93）无差别** |
| `net_ms` | 0.17/0.27/0.35 | 网络延迟统计正常 |
| `av_synced` | 173 | 音画同步正常 |
| `audio_depth_ms` | 40.0/60.0 | 音频缓冲深度正常 |
| `decrypt_failed` | 3 | 少量失败（见下） |
| `replay_rejected` | 1 | 重传被误判（见「重放窗口对重传误杀」） |

**关键结论：加密对延迟没有可测量的影响。** `playable_ms` p50 与未加密
完全一致（20.89 vs 20.94），这与基准测试的预测（8KB 帧加密 8.74µs =
延迟预算的 0.044%）吻合。

`decrypt_failed=3` 的原因：NACK 重传的帧在接收端会被重放窗口拦一次
（`replay_rejected`），但 FEC 恢复路径与正常路径各自独立计数，
所以同一帧可能在两条路上各被拒一次。这个统计口径需要统一（未做）。

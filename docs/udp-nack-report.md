# UDP + NACK 弱网实测报告

> 测试日期：2026-11-24
> 环境：Windows，同机回环（127.0.0.1），UDP + 应用层分片
> 配置：60 fps，每帧 8192 字节（切成 7 片），持续 10 秒

> ## ⚠️ 勘误（2026-11-24，`latency-bench` 子代理发现 + 主线独立复核）
>
> **本文第 1 节「0% 丢包 p50 = 23.06 ms」这个数字复现不出来。**
>
> 用当前二进制独立复测 9 次（3 轮 × 每轮 5 个统计窗口）：
>
> ```text
> 第 1 次：20.88, 20.91, 20.92, 20.91, 20.91
> 第 2 次：20.95, 20.95, 20.95, 20.96, 20.96
> 第 3 次：20.95, 20.96, 20.96, 20.95, 20.95
> ```
>
> **全部在 20.9 ms 附近，稳定复现不出 23.06。**
>
> ### 这条差异的实质影响
>
> 第 6 节原本的结论「UDP 版 p50 略高是因为分片带来了额外的一次遍历与拷贝」
> **不成立** —— 实测 UDP 与 WebSocket 的 p50 都是 20.95ms，没有差异。
>
> 分片开销确实存在，但落在 `net_ms`（0.2ms 量级），被 20ms 抖动缓冲完全淹没。
>
> **UDP 的代价不在 p50，而在 p95**：3% 丢包时 p95 从 22ms 跳到 58ms。
>
> 表格与结论保留原文（历史记录），但读的时候以本节为准。

## 1. 三种丢包率下的表现

| 丢包率 | 到达帧数 | p50 延迟 | p95 延迟 | p99 延迟 | NACK 请求 | 重传 |
| --- | --- | --- | --- | --- | --- | --- |
| 0% | 593 | 23.06 ms | 25.52 ms | — | 0 | 0 |
| 3% | 620 | 20.97 ms | 57.70 ms | 88.98 ms | 190 | 177 |
| 10% | 545 | 24.78 ms | 74.02 ms | 150.21 ms | 456 | 620 |

关键观察：

- **p50 几乎不受丢包影响**（20.97 vs 24.78，见上方勘误）—— 绝大多数帧还是准时到达
- **p95/p99 随丢包率显著上升** —— 丢包帧等重传补齐的代价，符合预期
- **3% 丢包时 healed=143** —— 延迟请求策略救回了 143 次乱序误报

## 2. 踩到的三个真 bug

### 2.1 NACK 收发 socket 不一致（最致命）

**现象**：服务端 nack_sent=324，发送端 retransmitted=0，cache_served=0。
重传链路完全断开，但两端日志都「看起来在工作」。

**根因**：发送端用一个独立 bind 的 socket 收 NACK，而服务端回包是发到
**数据报的源地址** —— 也就是发送 socket 的端口。那个端口没人读。

**修法**：用发送 socket 本身收。它已 connect 到接收端，recv 只会收到来自
该 peer 的包，正是所需：

```rust
let recv_socket = sender.socket();  // 不是 UdpSocket::bind("0.0.0.0:0")
```

**教训**：UDP 无连接，「我的地址」不是「我 bind 的地址」，而是「这个 socket 的地址」。

### 2.2 saturating_sub 导致刚标记的缺失立刻到期

**现象**：单测 missing_seq_is_not_requested_before_delay 失败，3ms 时就发出了请求。

**根因**：now_us.saturating_sub(delay_us) 在 now < delay 时返回 0，
而记录时刻也接近 0，所以 t <= 0 恒成立。

**修法**：改用 checked_sub，返回 None 就说明还没到时间。

### 2.3 请求后删除记录，导致重传再丢就没人管

**现象**：healed_before_request 永远是 0；重传包如果再次丢失，那个 seq 从此消失。

**根因**：poll() 一发出请求就 pending.remove(seq)。

**修法**：记录保留，按 retry_ms 间隔重发，超出 max_requests_per_seq 才放弃。
修复后 healed=143，这个数字就是延迟请求策略的实际价值。

## 3. 分片设计

### 为什么不用 IP 层分片

IP 分片丢任何一片，整个 IP 包作废，重传粒度是整个 8KB 帧。
应用层分片可以只重传丢的那一片，且能精确 NACK。

### 分片头（8 字节，紧随 32 字节帧头）

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 2 | fragment_index |
| 2 | 2 | fragment_count |
| 4 | 4 | total_size |

FLAG_FRAGMENT 置位表示存在这个头。重组后自动清除。

### 快速缺片检测

只靠超时（30ms）会让缺片帧白等到超时才发 NACK。但 UDP 有个性质：
**后面的包到了，说明前面的包已经过了网络层的最长可能路径**。

所以当 highest_completed_seq > seq + 3 时，可以断定 seq 的缺片不会再来了，
立刻报缺，不必等超时。

## 4. 当前链路全貌

```text
手机端                                    电脑端
────────────────────────────────────────────────────────────
Camera → 编码 → 分片(7片/帧) → UDP      UDP → 重组 → 抖动缓冲 → 出队
                    ↓                        ↑        ↓
              重传缓存 ←──── NACK ────── 缺片检测
              (300帧/5秒)      (延迟5ms+重发20ms)
```

## 5. 延迟预算更新

| 环节 | 无丢包 | 3% 丢包 |
| --- | --- | --- |
| 网络单程 | 0.19 ms | 0.21 ms |
| 分片重组 | 0 ms | 0~30 ms（视是否缺片） |
| 抖动缓冲 | 20.6 ms | 20.6 ms |
| 出队节拍 | 0.5 ms | 0.5 ms |
| **合计 p50** | **23.1 ms** | **21.0 ms** |
| **合计 p95** | **25.5 ms** | **57.7 ms** |

3% 丢包时 p50 反而略低 —— 因为丢包让到达帧数变少，
统计里「等重传的慢帧」被计入 p95/p99 而不是 p50。

## 6. 与 WebSocket 版对比

> **本节结论已被勘误推翻**，保留原文供对照。修正后的对比见下。

原文（**已失效**）：

| 指标 | WebSocket | UDP + NACK |
| --- | --- | --- |
| p50 | 20.83 ms | 23.06 ms |
| p95 | 21.82 ms | 25.52 ms |

> UDP 版 p50 略高是因为分片带来了额外的一次遍历与拷贝。

### 修正后的对比（实测，`docs/latency-matrix.md`）

| 指标 | WebSocket | UDP（0% 丢包） | UDP（3% 丢包） |
| --- | --- | --- | --- |
| p50 | 20.95 ms | **20.95 ms** | 21.00 ms |
| p95 | 21.97 ms | **21.97 ms** | **58.04 ms** |

**p50 没有差异。** 分片确实带来一次额外遍历与拷贝，但它落在
`net_ms`（0.2ms 量级），被 20ms 抖动缓冲完全淹没 —— 这是抖动缓冲
「吸收微小抖动」的设计目的，不是缺陷。

**UDP 的代价体现在 p95**：3% 丢包时 p95 从 22ms 跳到 58ms
（要等一个 RTT 的重传）。换来的是「丢包时不会队头阻塞」——
TCP 下一个包丢了整条流都停住，UDP 只停那一帧。

这个取舍仍然成立，只是**论据要换成 p95 而不是 p50**。

## 附录 C：一个被实测证伪的假设（第二十七轮）

### 假设

读代码时发现：发送端重传走 `cache.take_for_retransmit(s)` → `s2.send_frame(&f.bytes)`，
**原样重发缓存的密文，seq 不变**。而接收端顺序是
`重组完成 → replay.check_and_mark(stream_id, seq) → 解密`（`udp_server.rs` 837-861）。

看起来应该是：

```text
首传 seq=100 → check_and_mark(100) 通过，位图置位
重传 seq=100 → check_and_mark(100) 返回 Duplicate → replay_rejected += 1 → continue
```

即「开 `--psk` 后重传一次都不会生效」。这是一个看起来很有说服力的推理 ——
错误码对、调用链对、seq 语义对。**但它是错的。**

### 实测（`tools/verify-replay-retx.ps1`）

对照组：同一条代码路径，只切换 `--psk`；3% 丢包、无 FEC（让丢包全走 NACK）。

| 指标 | 无 `--psk` | 有 `--psk` |
| --- | --- | --- |
| sender `retransmitted` | 144 | 142 |
| sender `simulated_drops` | 140 | 139 |
| rx `nack_seqs` | 152 | 152 |
| rx `healed` | **119** | **116** |
| rx `replay_rejected` | **0** | **0** |
| rx `decrypt_failed` | 0 | 0 |
| `playable_ms` p50/p95 | 21.02 / 58.06 | 21.08 / 59.23 |

两组几乎完全一致，`replay_rejected` 都是 0。**重传正常工作，重放窗口没有误杀。**

### 为什么推理错了

关键在 `fragment.rs` 的 `push`：

```rust
if !entry.is_complete() { return None; }
let done = self.partial.remove(&key)?;   // ← 完成才 remove
```

而 **NACK 只为「未完成的帧」发出**（`expire` / `poll_stale` 返回的 `(stream_id, seq)` 列表）。
所以重传到达时，那个 seq 的 `partial` 条目**还在**，重传的分片填进原来的洞
→ **这是该 seq 的第一次完成** → `check_and_mark` 通过。

「重传 = 第二次到达」这个前提，在接收端视角根本不成立：
它到达的是**同一个半成品**，不是第二个完整帧。

要产生真正的重复，需要「原帧已靠后到的原始分片完成，重传才到」——
那要求重传延迟大于乱序窗口，而 NACK 是 5ms 批 + 20ms 重试，
RTT 在回环上 <1ms，这个窗口几乎不存在。实测 `replay_rejected=0` 与之吻合。

### 顺带确认的另一个事实

`FLAG_RETRANSMIT`（bit1）确实**全仓库无写入点**，重传复用 `FrameType::Video`。
后果只是统计口径：`frames` 计的是「到达尝试数」而不是「去重后的帧数」，
所以 `frames=493` 而 `av_synced=409`。不影响功能。

### 教训

**「代码读起来必然如此」不等于「运行时如此」。** 这次的推理链每一环都正确，
唯独漏了一个前提：「NACK 只为未完成的帧发出」。这个前提写在
`poll_stale` 的注释里，不在 `push` 的路径上 —— 读调用链时跳过了。

成本很低（写个 40 行脚本跑 16 秒），收益是**没有去改一个不存在的 bug**。
如果当时直接动手「修」，会往 `FrameSealer` / `ReplayGuard` 里加一个
「重传豁免」分支 —— 那是给正确代码引入复杂度，还会削弱重放防护。
